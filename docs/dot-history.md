# Dot History Specification

この文書は、保存された複数のDotを見渡して過去のDotへ戻る体験を扱う。MVP全体の範囲は
[`product.md`](./product.md)、録音からDot生成までの仕様は[`journaling.md`](./journaling.md)、
Dot生成後の任意の深掘り対話は[`dot-follow-up.md`](./dot-follow-up.md)を参照する。

## 1. Dotのモチーフ

Focus on Dotでは「Dot = その日の自分」を、UIで丸として表す。1日をひとつのDotとして見渡し、
時間が積み重なるとDot同士の関係や変化が見えてくる体験を目指す。保存は録音1回ごとに1件とし、
一覧の表示だけを日単位にまとめる。同日に複数回録音しても、過去の録音から生成したDotを
上書き・統合して失わない（下記「MVPの履歴ルール」）。

- Dotを単なる記録件数として扱わず、詳細を開かなくても時間の積み重ねを感じられるようにする。
- 色や大きさから感情を決めつけず、過去を評価する表現にしない。
- 演出より、振り返りやすさと現在地の分かりやすさを優先する。

## 2. MVPで必要な履歴体験

- 認証済み利用者が自分の保存済みDotを複数件見渡せる。一覧から過去の任意のDotを選び、その内容を振り返れる。件数が増えても過去のDotへ到達できる。
- Dayでは今日のDotを大きく表示する。そこから過去のDotの一覧へ進める。
- 一覧では各Dotを丸として表し、日付と選択対象を判別できる。色やサイズだけに意味を依存させない。
- Dotがない状態、読み込み失敗、選択した日のDotを取得できない状態、選択した日のDotが0件になった状態を、実際のデータ状態と矛盾せず示す。
- 他人のDotを一覧や詳細から取得できない。認証・認可、保存・削除の共通条件は`product.md`と`journaling.md`に従う。
- **ゴミ箱に入れたDotを、Dayにも一覧にも詳細にも出さない**（2026-09-29にTASK-002でゴミ箱を採用）。
  ゴミ箱の中身はゴミ箱の画面からだけ見え、復元すると一覧へ戻る。除外を暗黙の既定scopeに頼らず、
  一覧・Day・詳細のそれぞれで対象を明示する。件数や丸の並びにもゴミ箱の中身を含めない。

一覧の配置、並び順、日付境界、同日の複数録音、記録のない日の表現は下記「MVPの履歴ルール」で
決めた。検索、カテゴリ、期間フィルタは、このMVP受け入れ条件に含めない。

### MVPの履歴ルール（2026-09-29採用、未実装）

[TASK-004 Plan §17–§26](implementation-plans/2026-09-28-task-004-history-design.md)で採用した。
実装済みの挙動ではない。endpointとschemaの具体はTASK-005、保存・取得の実装はTASK-008、
画面の実装はTASK-012が扱う。

- **保存単位**: 録音1回ごとにDotを1件保存する。同日の再録音は追記であり、過去のDotを上書き・
  統合しない。表示上の「1日=1つのDot」は一覧の見せ方であり、保存件数ではない。
- **日付**: `date`は`recorded_at`（**録音開始操作をserverが受理した時刻**。UTCで保持。下の
  「`recorded_at`の決め方」で定義する）から算出したAsia/Tokyoの暦日とする。保存時刻（作成時刻）は
  基準にしない。送信・生成・保存の失敗を24時間以内に再試行しても、
  日をまたいだ録音でも、話した日から日付が動かないようにするためである。日付はserverが決め、
  clientの時計・タイムゾーンを根拠にしない。1日の始まりは0:00 JSTとし、深夜の録音を前日扱いに
  するオフセットは使わない。「最新」は`recorded_at`の降順、同値ならDotの識別子の降順で決める
  （Dayの「今日の最新」と詳細の既定表示は同じ規則を使う）。
- **`recorded_at`の決め方**: **録音開始操作をserverが受理した時刻**とする。実際の録音開始操作に
  対応して発行する録音attemptの受理時刻であり、認証確認（マイク起動前のログイン確認）の時刻は
  使わない。確認から実際の録音開始までは任意の時間差があり、確認だけして録音しない場合もある
  ためである。マイク権限の取得後、attemptの発行が成功した直後に録音を開始する順序をFrontendで
  守る（TASK-010）。それでもserverの応答時間・通信・browser側の処理の分だけ実際に話し始めた瞬間との
  差が残るため、**両者が完全に一致するとは扱わず、差が一定の秒数以内とも保証しない**。
  **この遅れが日付境界（0:00 JST）をまたいだ場合は日付がずれ得る**ことを受け入れる。端末が計測した
  開始時刻を送って採用する案は、端末の時計が日付の根拠に入るため採らない。attemptは本人に紐づき、
  **1つのattemptは1件のDot生成にしか使えない**。録音をやり直したら新しいattemptになり、古い
  attemptを別の録音へ流用できない。別Userへ入り直した後は前のUserのattemptを使えない。
  送信されないattemptには期限を設ける。期限は最長30分の録音と、停止から送信までの時間・失敗後の
  再試行の猶予を含めて設定し、録音中に切れて送信できなくなる値にしない。attemptの発行はserverへの
  往復を1回増やすが、マイク起動前の認証確認で往復は既に必須であり、オフラインで録音を開始できない
  経路が新たに増えるわけではない。発行に失敗したときは録音を始めず、次の操作を案内する。
  保存方式（serverに保存するか署名済みの値を端末のmemoryに置くか）と、録音中の失効から同一Userで
  復帰した場合の再利用の可否はTASK-005で契約化し、
  Frontendでの取得・保持・破棄はTASK-010が扱う。serverに保存する方式を採る場合は、未送信attemptの
  保持・期限・削除を[`privacy.md`](./privacy.md) §5へ追加する。
- **Day**: 今日のDotのうち最新の1件を大きく表示する。今日の記録がない場合は未記録であることと
  録音への導線を示し、過去のDotを今日の記録として表示しない。
- **一覧**: 1日を1つの丸として、新しい順に並べる。記録のある日だけを詰めて並べ、記録のない日は
  枠を置かない。見出しテキストは年と月を示し（例: 「2026年9月」）、年が変わる位置でも現在見ている
  年が分かるようにする。各丸には日付の数字をテキストで添え、同日に複数のDotがあるときは件数を
  補助テキストで示す。今日には「今日」のラベルを添える。
- **丸の表現**: MVPでは色・サイズに意味を持たせず、すべて同一とする。丸を線で結ばない。
  選択中とフォーカスは枠線とテキストで示し、色だけで状態を伝えない。各丸は十分なタップ領域
  （最小44px）と、年月日を含むアクセシブルな名前（例: 「2026年9月28日のDot」）を持つ。
  複数年を使っても同名の選択肢が並ばないようにする。
- **詳細**: 丸を選ぶとその日のDotを振り返れる。取得は**日付をキー**にし、その時点でゴミ箱の外に
  ある同日のDotを対象とする。一覧が持つ最新Dotの識別子を、日の詳細へ到達する唯一のキーにしない
  （一覧を取得した後にその1件がゴミ箱へ移っても、同日に残っているDotへ到達できるようにする）。
  同日に複数あるときは録音時刻のラベルで切り替え、既定は最新のDotとする。時刻はJSTで表示する。
  その日のDotが多いときの取得の続きはTASK-005で定めるが、**日を開けばその日のすべてのDotへ
  到達できる**ことを満たす。
- **取得**: 一覧は日単位の要素を新しい順に返し、続きはcursorでたどる。日単位の集約はserverで
  完結させ、ページの境界で同日が分断されないようにする。offsetやpage番号は使わない。
  1要素は日付・その日の件数・最新Dotの識別子といった**件数に依存しない固定サイズ**とし、
  同日の全Dotの一覧はその日を開いたときに取得する。同日の録音件数に上限はないため、
  一覧の1要素へ全件を並べない。
  「過去の任意のDotへ到達できる」は、一覧の続きを最後までたどれることと、日を開けばその日の
  すべてのDotへ到達できることの両方で満たす。任意の月へ直接ジャンプする操作は期間フィルタとして
  対象外のままとする。
- **状態の区別**: Dotが一件もない状態、一覧の読み込み失敗、続きの取得失敗、**選択した日のDotを
  取得できない状態**、**選択した日のDotが0件になった状態**を区別する。続きの取得に失敗しても
  取得済みの一覧を空にせず、取得できない日や取得できないDotを別のDotで代替表示しない。
  0件は、一覧を取得した後にその日のすべてのDotがゴミ箱へ移るか完全削除されると起きる。
  取得失敗と同じ扱いにせず、その日に振り返れるDotがないことを示し、一覧を取り直してその日の
  要素を更新する（古い一覧に丸が残ったまま空の詳細を見せ続けない）。
- **ゴミ箱との関係**: 上のゴミ箱の扱いに従い、ゴミ箱の中のDotを日単位の集約にも件数にも含めない。
  同日のすべてのDotがゴミ箱にある日は丸を出さない。Dayの「今日の最新」もゴミ箱の中のDotを
  選ばない。復元すればその日の丸と件数へ戻る。

一覧・詳細で表示するDotは、`dot-follow-up.md`が扱う深掘り対話により後から更新され得る。更新後の
表示方法、最初に生成された内容と現在の内容の区別、更新履歴の参照方法は、このMVP受け入れ条件には
含めず、深掘り対話の実装前の判断として`dot-follow-up.md`とTASK-018で決める。

## 3. 時間軸の検証候補

Dayで今日のDotを見る体験を起点に、次の時間軸表現を`Concept → Prototype → User Test → 採用判断`
で検証する。Week / Month表示とズームの動きはMVP完成条件ではない。

| 視点 | 表現案 |
| --- | --- |
| Week | Dayから視点を引き、1週間を7つのDotで見渡す。Dayで選択していたDotを見失わない。 |
| Month | さらに視点を引き、約1か月のDotを俯瞰する。 |

時間軸の切り替えでは、iPhone Photosのように視点が引いていく感覚を参考にする。DayからWeek、
WeekからMonthへ進んでも、選択中のDotと時間のつながりが分かることを優先する。左端への配置、
タブ・ピンチ・スクロールの操作、具体的なアニメーションは未決定である。動きを減らしたい利用者への
配慮も採用判断に含める。

プロトタイプでは、Dotの集合から時間の積み重ねを感じられるか、切り替えが分かりやすいか、
動きや丸いモチーフが振り返りと情報の読みやすさを助けるかを確認する。

## 4. AIによる振り返りの段階

MVPは個々のDotに対する日々の振り返りを扱う。週次の「今週のDotから見えてきたこと」と月次の
「今月の変化や繰り返していたテーマ」は将来候補とする。長期的には`Dot → Line → Pattern`、
すなわち日々の自分、複数Dotのつながり、長期的な傾向という体験を検討する。

## 5. 未決定事項

- 利用者ごとのタイムゾーン設定。国外での利用または日付のずれの申告があれば再検討する。
  既存Dotの日付を再算出できるよう、録音時刻をUTCで保持することを前提とする
- 深夜の録音を前日として扱うオフセット。0:00 JST境界で違和感の申告が出た場合に再検討する
- 同日の複数Dotを1つへまとめる表現。`Dot → Line → Pattern`の検討に含める
- 録音attemptの保存方式（serverに保存するか署名済みの値を端末のmemoryに置くか）、未送信attemptの
  期限の具体値、録音中の失効から同一Userで復帰した場合の再利用の可否。いずれもTASK-005で契約化し、
  server保存を選ぶ場合は[`privacy.md`](./privacy.md) §5へ保持・期限・削除を追加する
- Weekの開始曜日、Day / Week / Monthの操作とアニメーション
- 週次・月次AI振り返りを読みたいと感じるか、採用する場合の生成・保存方法
- 深掘り対話による更新後のDot表示、最初の生成内容と現在の内容の区別方法、更新履歴の参照方法
  （詳細は[dot-follow-up.md](./dot-follow-up.md)と[TASK-018](./tasks/TASK-018-dot-follow-up-dialogue-design.md)）

これらを未決定のまま実装へ持ち込まない。MVP一覧に直接必要な事項は§2の「MVPの履歴ルール」で
決めた。残る事項は、関連するImplementation Planで決めてから実装する。
