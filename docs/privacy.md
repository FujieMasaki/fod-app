# Privacy and Personal Data Specification

この文書は、Focus on Dotで録音・生成・保存する個人データを減らすための**プロダクト横断の仕様と設計上の制約**である。
現在の実装を表す文書ではない。録音からDotまでの現行動作とMVP受け入れ条件は[journaling](./journaling.md)、
認証・公開基盤は[architecture](./architecture.md)、変更差分の確認方法は`code-review/`を正本とする。

**データの保持期間と削除の契機は§5を正本とする。**他の文書は§5を参照し、期間や契機を書き写さない。
食い違いがあれば§5を優先して他方を直す。

## 1. 前提と適用範囲

- 音声ジャーナルには、利用者本人だけでなく、家族・知人・勤務先など第三者の名前や私的な情報も入り得る。
  名前を入力項目として求めなくても、アカウントと紐づくDot、音声、文字起こしは慎重に扱う。
- 物品配送に必要な住所、本人確認書類、カード番号などをMVPの入力項目として要求・収集しない。
  自由な発話に含まれる可能性は残る。将来これらの入力が必要になった場合は、収集の必要性、
  外部サービスへの委託、保持・削除、運用負担を別途判断する。
- 本人が自分の心身の状態や通院について話すこともある。感情の記録すべてが要配慮個人情報に
  当たるわけではないが、該当する個人データの漏えい等は報告・本人通知の対象になり得る。
  該当範囲と漏えい時の対応はTASK-017で判断し、この文書では該当し得る前提だけを置く。
- 氏名だけを置換しても、関係性、場所、出来事などの組み合わせから人物を推測できる場合がある。
  固有名詞の置換を「匿名化済み」や「漏えいしない」と表示・記録しない。
- 外部サービスに処理を委ねる場合も、送信する内容・委託先での保持・削除・アクセス条件の確認と、
  利用者への説明はFocus on Dotの責務として残る。
- 認証方式はTASK-001で採用済み。メールアドレス、password hash、確認・再設定関連情報、Google識別子は
  設計上RDSに、通常のCookie sessionは利用者端末に置く。認証データの経路と責務の正本は
  [architecture](./architecture.md)と[TASK-001 Plan §47](./implementation-plans/2026-09-21-task-001-identity-design.md)とする。
- Dot生成後の任意の深掘り対話でも、初回録音と同様に第三者の名前や私的な情報が新たに話され得る。
  対話由来のデータの扱いは本文書の原則に従い、体験方針は[dot-follow-up.md](./dot-follow-up.md)を参照する。

## 2. MVPで守る原則

本節はデータ取扱いの設計上の制約である。録音体験のMVP受け入れ条件は[journaling §4](./journaling.md)、
MVP全体の範囲は[product](./product.md)を正本とする。

1. **データを減らす。** 音声原本、文字起こし全文、Dot、認証情報、ログを分け、目的に不要な項目を
   収集・送信・保存しない。2026-09-28にTASK-002で、**音声原本と文字起こし全文を長期保存せず、
   長期保存するのはDot（`sentence`と話した内容の要約`summary`）だけ**と決めた。音声はDotができる
   までの一時的な預かりに限り、Dotの保存まで完了した時点で即削除、失敗した場合も再試行期限のあとに
   削除する。**「長期保存しない」は「一時的にも置かない」という意味ではない。**2026-09-29に
   TASK-003で、文字起こし全文を端末が受け取るまでS3へ一時的に置くこと、後片付けに必要な処理の記録を
   片付けが終わるまで持つことを決めた。**一時的に置くデータも§5-1に行として並べ、保持しないデータ
   として扱わない。**期間と削除の契機は§5を正本とする。
   **利用者への説明でも一時的に預かる事実を隠さない。約束するのは「やり直せる期限」と
   「いつ削除処理を始めるか」であって「消える期限」ではない。**
   要約は「何を話したかを思い出せる」という目的があるから保存するのであって、要約だから安全という
   意味ではない。第三者の実名は要約にも残り得るため、Dot本文と同じ保護・削除・説明の対象にする。
   **この判断は仕様であって実装ではない。決めた保持・削除を実装済みと扱わない。**
2. **送信より前の境界を確認する。** 文字起こし後に名前を置換しても、外部の文字起こしサービスへ
   音声を送っていれば、そのサービスには元の音声が届く。外部AIに渡る最初の地点をデータフローに示す。
3. **利用者が判断できるようにする。** 説明や選択の時点を、元データの送信・保存より前に置く。
   録音前の案内に関する受け入れ条件は[journaling §4](./journaling.md)を参照する。
4. **検出を過信しない。** 人名・地名・組織名等の検出には見逃しと誤判定がある。利用者の言葉を
   確認なく別の関係に書き換えない（例: 「タカシ」から「長男」と決めつけない）。
   置換・削除・録り直し等の導線を採用する場合は、元データの送信・保存前に選べるよう設計する。
5. **保存後も残存を管理する。** Dot、音声、一時ファイル、外部AI側のデータ、端末、ログ、バックアップを
   対象に、保持期間と削除方法を決める。名前が含まれたことを保存後に知らせるだけでは、
   既に保存・送信された元データのリスクは解消しない。保存後に検出した場合は、
   利用者を責める注意だけでなく、残っているデータと削除・修正の手段を示す。
   MVPの手段は**Dot本文の編集、1件ごとの削除、退会**である（2026-09-29にTASK-002で編集を追加）。
   **修正の手段を、削除で代替しない。**Dotは録り直せないため、他人の実名が入った一文を直せずに
   Dot全体を捨てるしかない状態は、原則を満たしているとは言えない。
   **アプリは編集前の値を残さない。**消したかった記述が編集履歴に残るのでは、直した意味がない。
   ただし**「履歴を持たない」と「旧い値がどこにも存在しない」は別である。**編集より前に取得した
   backupには旧い本文が残る。復元したときに、**削除したデータと編集で取り除いた内容を再び見える
   状態にしない。**削除の再適用だけでは、編集されたデータは削除対象にならず本文ごと巻き戻る。
   1件ごとの削除はゴミ箱を経由し、受理から7日で削除処理を始める。ゴミ箱に入れた状態を「削除しました」と
   表示しない。**消え終わる時刻も約束しない。**「完全に削除」が指す範囲（自分たちが持つ分か、
   backupや委託先を含むのか）を、利用者に分かる形で示す。**ゴミ箱を経由しない「すぐに完全削除」も併せて備える。**「今すぐ消したい」に
   7日待たせない。削除の対象には、処理が終わらずに残っている一時的な音声も含める。
   削除が複数の保存先にまたがる場合、一部しか消えていない状態を「削除しました」と表示しない。
   **保存先の自動削除機能（S3のlifecycle等）が消す時刻を、利用者へ約束する期限に使わない。**
   指定した日数は「削除対象になるまで」であり、その後の削除も遅延し得るため、**削除が完了する
   時刻の上限にならない。**約束できるのは、アプリが自分で消す条件（いつ削除処理を始めるか）と、
   障害時には遅れ得ることまでである。
   **「削除した」が実体の消去を意味しない設定がある。**版管理・複製・世代保護などが有効だと、
   削除操作が成功しても元のデータが別の版や別の場所に残る。保存先ごとに、削除が実体を消すことを
   設定で確認してから「消える」と説明する。既定値がそうなっているはずだ、と仮定しない。
   進行中の処理がある状態での削除は、数えて消すだけでは漏れる。**削除の受理以降に新しい保存・
   再試行・結果の確定が起きないようにし、あとから現れた残存を回収してから完了とする。**
   自分たちのデータを消しても外部の委託先に残り得るため、「完全に削除した」とは表示しない。
   RDSのbackup保持期間内は削除済みのDotがbackupに残るので、復元時に削除要求を再適用する。

## 3. 送信・保存フローを決める際の確認表

| 段階 | 決めること | 確認するリスク |
| --- | --- | --- |
| 録音前 | 利用者への説明、実名等を言い換える案内 | 内容を知らないまま録音・送信されないか |
| 音声取得 | 端末内の一時保持、失敗・中断・再試行、原本保存の採否 | 原音声に名前が残ること、端末内やサーバー内の残存 |
| 文字起こし | 採否、端末内か外部か、送信先・保持・削除 | 外部処理では置換前の音声が届くこと |
| AI生成前 | テキスト化する場合の固有名詞等の低減方法、誤判定時の扱い | 置換漏れ、文脈を壊す置換、他の記述からの推測 |
| Dot保存 | 保存する項目、本人限定アクセス、名前を含む結果の確認・修正・削除 | 生成結果にも個人情報が残ること |
| 深掘り対話 | 対話音声/テキスト・AI入出力の送信・保存要否、反映前の変更案の保存範囲、承認済み変更のみDotへ反映する運用 | 対話中に新たな実名等が話されること、未承認の提案がDotの正本と混同されること |
| 削除・障害 | 一時データ・外部先・ログ・バックアップ、失敗時の再実行 | 消去漏れ、削除済みデータの復活、誤った完了表示 |

各段階についてTASK-002で決めた結論は
[TASK-002 Plan §17・§22](./implementation-plans/2026-09-28-task-002-data-lifecycle.md)、
経路と境界は同§9、残存の追跡は同§24にある。表はこの先の変更でも同じ観点を確認するために残す。

### 5-1. データ別の条件

| データ | 保持する目的 | 起点 | 削除を始める条件 | 完了の扱い | 残る例外 |

### 5-2. 利用者へ約束できること・できないこと

| 約束できる | 約束しない |
| --- | --- |
| 何を送るか、どこへ渡るか | 外部へ渡った内容を即時に消せること |
| 何を残し、何を残さないか | 消え終わる時刻（「◯時間で消えます」「どこにも残りません」） |
| いつまでやり直せるか（受理から24時間、期限日時をserverが返す） | lifecycle等の自動削除機能の設定値を消去の期限として |
| 何を契機に削除処理を始めるか | 期間の足し算による合計の保持期間 |
| 障害時には削除が遅れ得ること | 「完全に削除しました」（範囲を示さずに） |

**「完全削除」が指すのはアプリが持つ分**（`dots`の行、残っていれば音声の一時object、**文字起こし
結果のobjectと対応するAmazon Transcribeのjob**、**そのDotを作った処理の記録**）である。
RDS自動backupと外部providerに残り得る分は含まない。その2つは別の説明として示す。
**削除の受理と、削除処理の完了は別である。**受理した時点から文字起こし全文は返さなくなるが、
実体が消え終わる時刻は約束しない。

### 5-3. backupと復元の扱い

- RDS自動backupの保持期間内は、**削除したDotも、編集前の本文も残る。**アプリが履歴を持たないことと、
  旧い値がどこにも存在しないことは別である。
- 復元したときに、**削除したDotと、編集で取り除いた内容を再び見える状態にしない。**削除要求の再適用
  だけでは足りない。編集されたDotは削除対象ではないため、復元すると本文が編集前へ巻き戻る。
- 実現方法はTASK-013/015で決める。どの方法を採っても、**編集前の本文をアプリの保存領域へ持たない**
  制約は維持する。
- backup内の旧い値そのものを一切残さないところまで求めるかは未確定で、公開までに許容範囲と説明を
  確定させる。
