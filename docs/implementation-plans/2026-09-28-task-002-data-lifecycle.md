## 2. Goal

録音した音声、文字起こし、Dot、録音時間、ログについて「誰が受け取り、どこに残り、いつ・誰が消すか」を
一つのデータフローとして説明できる状態にする。利用者が録音前に何が送られるかを知り、後から自分の
データを消せる条件を、実装前に仕様として確定する。

## 7. Proposed Approach（推奨案・未承認）

§18–§21の推奨をまとめると次のとおりである。各案の比較は該当節を参照する。

1. 音声は実サービスへ送る。経路は同一originのRails経由（multipart）で、Railsが認証・所有者・形式・
   size を検証してから外部の文字起こしへ渡す。**音声原本はRDSにもS3にも保存しない。**成否に
   かかわらず処理直後に一時ファイルを削除し、取りこぼしに備えて短いTTLでも強制削除する（§18案A）。
2. **文字起こしは保存しない。**生成の入力として通過させるだけで、DBに列を作らず、ログにも出さない（§19案A）。
3. 残るのはDot（sentence / reflection / closing / date / duration）だけで、RDS東京が正本。端末の
   localStorageは正本にしない（§17）。
4. 削除は**Dotの個別削除と退会の両方**をMVPに入れる。削除は物理削除とし、削除できなかったときに
   削除済みと表示しない（§20案A）。
5. **生成結果の編集は持たない。**訂正手段は削除して録り直すこととし、journalingの「更新」の表現を
   これに合わせる（§21案A）。
6. 録音前（認証確認の後、マイク起動の前）に、送信先・保存しないもの・残るもの・削除できること・
   他人の実名は言い換えられること・外部へ渡った内容の即時削除は保証できないことを知らせる（§22）。
7. 端末の既存`fod.session.v1`は、実サービス化の変更で読み取りをやめ、起動時に削除する（§22）。

## 8. Why This Approach

- privacy.md §2原則1（データを減らす）と§4の初期案（音声原本の長期保存と全文文字起こしの保存は
  避ける方向で比較する）に沿う。保存しない判断をここで確定するため、以後「未決定なのに保存しない
  と説明する」状態がなくなる。
- 保存物をDotだけに絞ると、削除連鎖・暗号化・lifecycle・孤児データの回収という運用が増えない。
  ECS 1タスク・Single-AZという現在の小さな構成（architecture）と釣り合う。
- 認証・所有者判定・size検証・破棄をRailsの一箇所に置けるため、「誰の音声か」の判定とCSRF・Cookieの
  扱いをTASK-001の採用（同一origin・CookieStore）から変えずに済む。
- 代わりに払う対価は「生成に失敗したら録り直し」である。これは実装の都合ではなく保持しない判断の
  結果なので、画面の文言と再試行の挙動を同じ変更で一致させる（§22、TASK-010/011）。

## 9. Data Flow（推奨案・未承認）

```text
[録音前]
Home / /record 直アクセス
  → Railsで認証・メール確認・7日期限を確認（journaling「録音前認証」）
  → 送信内容と残るもの・削除できることを知らせる案内を表示
  → 利用者が了解して初めて getUserMedia（マイク起動）

[録音〜送信]
MediaRecorder（browser memory のみ。localStorage へ書かない）
  → 停止（最長5分 / 上限到達で自動停止）
  → POST /api/v1/dots（同一origin・multipart・Cookie + CSRF）★音声が端末を出る境界
       ↓ Rails: 認証再確認 → 所有者決定 → content type と size を検証 → 一時ファイル
       → 外部文字起こしへ送信              ★★元音声が外部（第三者）へ渡る最初の境界
       → 文字起こしテキスト（memory のみ）
       → 外部AIへ送信                      ★★★発話内容が生成AIへ渡る境界
       → Dot を RDS 東京へ保存（user_id で所有者を固定）
       → ensure: 一時ファイルを削除（成功・失敗のいずれでも）
  → response は Dot のみ（音声URL・文字起こしを返さない）

[保存後]
RDS dots（正本） ─ 一覧・詳細は current_user.dots scope
  → 個別削除: dots の行を物理削除
  → 退会: user と dots を削除、session を破棄
  ※ 外部provider側に渡った内容の即時削除は保証しない（利用者へ説明する）
  ※ RDS 自動backup の保持期間内は削除済みデータが backup に残る

[保持しないもの]
音声原本: RDS / S3 へ保存しない。端末にも localStorage へ書かない
文字起こし: 保存しない（DB に列を作らない、ログに出さない）
```

★の3点が、privacy.md §2原則2が「データフローに示す」ことを求めている境界である。★★以降は
Focus on Dot側で削除しても委託先に残り得るため、録音前の案内に含める（§22）。

## 13. Risks / Things to Watch

- **再送できないことの説明責任。** 音声を保持しないため、生成失敗時は録り直しになる。現行の
  「音声は保存されています」という文言を残したまま実装すると、実挙動と矛盾した説明になる。
- **外部へ渡った内容は消せない。** Dotを削除しても、委託先の保持期間内は入力が残り得る。
  「削除しました」の表示範囲を自分たちのデータに限って書く必要がある。
- **backupからの復活。** 障害復旧でRDSを復元すると、削除済みのDotが戻り得る。復元手順に削除要求の
  再適用を含めないと、消したはずのデータが再出現する。
- **一時ファイルの取りこぼし。** 例外・タイムアウト・タスク終了で一時ファイルが残る経路がある。
  ensureでの削除に加え、TTLでの強制削除と、残存の検知方法が必要。
- **録音形式のbrowser差。** Chrome系のwebm/opusとSafariのmp4/aacで、外部文字起こしの受容形式が
  異なる可能性がある。TASK-003で確認しないまま上限や形式を実装すると、Safariだけ失敗し得る。
- **ログへの流入。** 例外のbacktraceやrequestのdumpに音声のファイル名・文字起こし・Dot本文が
  混ざる経路がある。既定で本文をログへ出さない設定と、例外時の出力範囲を確認する。
- **端末の旧データ。** `fod.session.v1`はmockと実データを区別しておらず、共有端末では別Userに
  前の利用者のDotが見える。実サービス化の変更で確実に破棄する必要がある。

## 18. 判断1: 音声の経路と原本保存（未承認）

### 案A（推奨）: Rails経由で送り、原本は保存しない

- 経路: Browser →（同一origin・multipart・Cookie + CSRF）→ Rails → 外部文字起こし → 外部AI → RDS。
  音声はRailsの一時ファイルとしてのみ存在し、成否にかかわらず削除する。
- 利点: 保存物がDotだけになる。認証・所有者決定・形式とsizeの検証・破棄をRailsの一箇所に置ける。
  S3のbucket・暗号化・lifecycle・アクセス制御・削除連鎖・孤児objectの回収が不要。追加の保存費が
  発生しない。privacy.md §2原則1と§4の初期案に沿う。
- 欠点: 生成失敗時に音声が残っていないため、利用者は録り直しになる。upload中はPumaのworkerが
  占有される（5分の録音で数MB程度と見込むが実測が必要）。ErrorStateの文言を変更する必要がある。

### 案B: S3東京へ短期保存し、失敗時は同じ音声を再処理する

- 経路: Browserがpresigned URLでS3へ直接upload → RailsがJobで取得 → 文字起こし → AI → RDS。
  objectはlifecycleで自動削除（例: 1日）。
- 利点: 生成・保存の失敗やJob再実行で録り直しが要らない。障害調査で実際の入力を確認できる。
  Railsのupload占有が短い。
- 欠点: 保存物が増える。Dot削除・退会でobjectも消す削除連鎖、失敗時の孤児object回収、暗号化と
  アクセス制御、presigned URLの発行範囲の誤りで他人のobjectへ到達しないことの検証が必要になる。
  privacy.md §4の「避ける方向で比較する」に逆行する。MVPでこれを採る根拠は再送UXだけである。
- 従量費は小さいが、運用と検証の負担はMVPの規模に対して大きい。

### 案C: 音声を外部へ送らず、端末内で文字起こししてテキストだけ送る

- Web Speech API: Chrome・Safariの実装はいずれもサーバー側の認識に依存し、端末内で完結しない。
  つまり音声はGoogleやAppleへ渡るため「外部へ送らない」を満たさない（採否の前に一次資料の確認が必要）。
- 端末内モデル（Whisper WASM等）: モデルのdownloadが数十〜数百MB規模で、mobileでの実行時間・電池・
  精度が課題になる。MVPの規模と釣り合わない。
- したがって「固有名詞を含む元音声が第三者に渡らない」をMVPで成立させる現実的な手段はない。これは
  privacy.md §2原則2が「明示する」よう求めている事実であり、案A・案Bのどちらでも利用者に説明する。

### 推奨

**案A。** 保持しない方針を最も素直に満たし、運用と検証の追加が最も少ない。対価は「失敗したら
録り直し」であり、これは仕様として説明できる。

### 案A採用時の送信仕様（既定案）

- 経路: 同一originの`POST /api/v1/dots`（`multipart/form-data`）。認証Cookieとcsrf tokenを検証し、
  所有者はserverのcurrent_userで決める。clientのuser_idを信用しない。正式な契約はTASK-005。
- 形式: 現行は`new MediaRecorder(stream)`でmimeType未指定のため、Chrome系は`audio/webm;codecs=opus`、
  Safariは`audio/mp4`が一般的である。serverは受容するcontent typeを列挙して検証し、非対応なら
  保存も外部送信もせず録り直しを案内する。外部文字起こしが受け付ける形式はTASK-003で確認する。
- 上限: 録音は最長5分とし、到達時は自動停止してその時点までを送る。requestの上限は10MB。
  目安として5分はopus 32kbpsで約1.2MB、AAC 64kbpsで約2.4MBであり、10MBは余裕を持った上限である
  （実測で見直す）。上限超過はserverが拒否し、音声を外部へ送らない。
- responseに音声のURL・文字起こしを含めない。

## 19. 判断2: 文字起こしの保存範囲（未承認）

- **案A（推奨）: 保存しない。**生成の入力として通過させるだけ。DBに列を作らず、ログにも出さない。
- 案B: 全文をRDSへ保存する。後から読み返せ、将来の週次・月次振り返りの入力にもなる。
- 案C: 要約やキーワードだけ保存する。

判断の材料:

- product.md §2のMVP完成条件に文字起こしの表示は含まれず、週次・月次AI振り返りは§3で「検証候補」、
  §4でMVP対象外である。案Bを今必要とする受け入れ条件がない。
- 案Bは個人データの量が最も増える。文字起こしはDotより生々しく、第三者の実名を含む発話がそのまま
  長期保存される。保存するなら保持期間・表示・削除・説明をすべて追加で決めることになる。
- 案Cは「何を残すかの判定」を新たに設計する必要があり、privacy.md §2原則4（検出を過信しない）に
  照らすと、残す・残さないの誤りを利用者が確認できないまま固定してしまう。

推奨: **案A。**将来必要になった時点で、保持期間と説明を含めて再判断する（product.md §5の保留事項に残す）。

## 20. 判断3: 削除要求の受け付け方（未承認）

- **案A（推奨）: Dotの個別削除と退会（アカウント削除）の両方をMVPに入れる。**
- 案B: 退会のみ。個別削除は将来。
- 案C: 個別削除のみ。退会は問い合わせでの運用対応。

判断の材料:

- journaling.md §4は「保存されたDotは認証済み利用者本人だけが取得・更新・削除できる」をMVP受け入れ
  条件に既に含め、TASK-013が削除と残存の検証を担当する。案Aが現行仕様と整合する。
- 案Bだけでは「1件だけ消したい（他人の実名を言ってしまった）」に応えられず、privacy.md §2原則5の
  「残っているデータと削除・修正の手段を示す」が成立しない。
- 案Cは「全部消したい」に自動で応えられず、運用の手作業と本人確認の手順が増える。

### 案A採用時の削除仕様（既定案）

- **Dotの個別削除:** `dots`の行を物理削除する。論理削除にしない（残す目的がなく、privacy.md §2原則1に
  反する）。音声・文字起こしは案Aでは既に存在しない。
- **退会:** userとそれに属するdots、認証情報を削除し、sessionを破棄する。コピー済みCookieの即時失効は
  保証しない（architecture既記載）。
- **外部provider側:** Focus on Dot側の削除は委託先のデータを消さない。委託先の保持期間内は入力が
  残り得ることを削除時の表示と録音前の案内に含め、「完全に削除しました」と書かない。
- **backup:** RDS自動backupの保持期間内は、削除済みのDotがbackupに残る。障害復旧で復元した場合に
  削除済みデータが再出現し得るため、復元手順に「復元後の削除要求の再適用」を含める（TASK-013/015へ引継ぎ）。
- **生成中の削除:** Dotの行がまだないため、削除対象が存在しない。MVPでは進行中の処理を止める操作を
  持たず、生成が終わってDotができた後に本人が削除する。TASK-003が非同期生成を採る場合は、待ち時間の
  長さに応じてcancelの要否をそちらで再判断する。
- **削除の失敗:** 単一のRDS transactionで完結するため部分成功は起きにくい。失敗時は削除済みと表示せず、
  失敗した旨と再実行の手段を示す（privacy.md §2原則5の「誤った完了表示」を避ける）。
- **削除の認可:** `current_user.dots.find`相当で本人のDotに限る。他人のIDを指定しても存在しない扱いにする。

## 21. 判断4: 生成結果の編集（更新）の要否（未承認）

journaling.md §5は「編集・削除」を未決定に含め、TASK-002の完了条件は「更新可能なデータと手段の要否を
明記し、編集UI等の追加が必要ならまず仕様の採用判断を行う」ことを求めている。

- **案A（推奨）: 編集を持たない。**訂正手段は「削除して録り直す」。更新APIも編集画面も作らない。
- 案B: Dot本文（sentence / reflection / closing）の編集をMVPに入れる。
- 案C: 編集はせず、非表示（アーカイブ）だけ持つ。

判断の材料:

- product.md §2の完成条件と§4の対象外に編集は現れない。journaling.md §4の「取得・更新・削除」は
  本人だけが操作できるという**認可の記述**であり、編集UIの採用を意味しない。
- privacy.md §2原則5が求めるのは「残っているデータと削除・修正の手段を示す」ことである。削除があれば
  原則は満たせる。Dotは本人の発話から生成された短文であり、一部を直すより消して録り直す方が意図に近い。
- 案Bは画面・API・編集前の値の扱い（履歴を残すか）が増え、MVPの完成条件を広げる。生成結果を編集

推奨: **案A。**採用する場合、journaling.md §4の「取得・更新・削除」を、MVPでは更新の手段を持たないと
分かる表現に改める（仕様の変更として本Planで判断する）。

## 22. 質問にしない既定案（未承認）

慣例的な既定値、または既存文書から導ける事項として、次を既定案とする。§23の判断で方向が変われば
合わせて見直す。

### 保持期間

- Dot: 本人が削除するか退会するまで。期間による自動削除はしない（振り返りが目的のため）。
- 音声・文字起こし: 処理中のみ。TTL 15分で強制削除。
- ログ: 既定14日。RDS自動backup: 既定7日。いずれもarchitectureの「backup保持/復元目標」「監視の
  具体値」が未決定のままなので、公開前に実値を確定する。

### ログに出さないもの

音声（内容・ファイル名）、文字起こし、Dot本文、Cookie・session値、Google callbackのcode、確認・
再設定token、メール本文。出すのはuser_id・dot_id・処理段階・結果・所要時間まで。ALB access logは
初期無効（architecture既記載）。例外のbacktraceやrequest dumpに本文が混ざらないことを実装時に確認する。

### 録音前に知らせる内容

認証確認の後、マイク起動の前に次を示す（journaling.md §4の受け入れ条件と「録音前認証」に整合）。

1. 音声を実サービスへ送ること。自分たちのserverを経由して、外部の文字起こしとAIへ渡ること。
2. 音声原本と文字起こしは保存せず、残るのはDotだけであること。
3. Dotは本人だけが見られ、いつでも削除できること。
4. 他人の実名・住所・連絡先は、必要がなければ言い換えられること。
5. 外部へ渡った内容の即時削除は保証できないこと。
6. 固有名詞の置換を行う場合でも見逃しがあるため、「匿名化済み」とは言わないこと（置換の採否はTASK-003）。

### 失敗後に実際に残るデータと再送可否（推奨案の場合）

| 失敗・中断の起点 | 端末 | Railsの一時領域 | RDS | 外部 | 再送 |
| --- | --- | --- | --- | --- | --- |
| 録音中に離脱・タブを閉じる | 何も残らない（memoryのみ） | なし | なし | なし | 不可（録り直し） |
| 権限拒否・非対応 | なし | なし | なし | なし | — |
| 送信失敗（network） | memoryのBlobのみ（画面に留まっている間） | なし | なし | なし | 同じBlobで再試行できる |
| 送信時に認証失効 | memoryのBlobのみ | なし | なし | なし | 再ログイン後、同一Userなら再試行できる。別Userへ入り直した場合は送らない |
| 文字起こし・AIの失敗 | なし | 削除済み | なし | **音声が渡った事実は残る** | 録り直し |
| 保存（RDS）の失敗 | なし | 削除済み | なし | 音声・テキストが渡り、生成は消費済み | 録り直し |
| 生成成功後に応答が届かない | なし | 削除済み | Dotが存在し得る | 渡り済み | 再試行せず、一覧で結果を確認できるようにする（冪等性の手段はTASK-003） |

現行ErrorStateの「音声は保存されています。もう一度試してください。」は実装と一致しない
（journaling.md §3が既に差異として記録）。推奨案では送信前の再試行だけが同じ音声で可能なので、
表示文言と実際の再試行可否を同じ変更で一致させる（TASK-010/011）。

### 端末の既存`fod.session.v1`

実サービス化の変更で、このkeyの読み取りをやめ、起動時に`removeItem`して破棄する。新しい永続keyを
作らず、Dotの正本をRDSにする。表示のcacheが必要になった場合も別keyにし、本人性の根拠にしない。
理由は、旧keyがmockと実データを区別しておらず、共有端末では別Userに前の利用者のDotが見えるためである。
TASK-010/014へ引き継ぐ。
