## 2. Goal

録音した音声、文字起こし、Dot、録音時間、ログについて「誰が受け取り、どこに残り、いつ・誰が消すか」を
一つのデータフローとして説明できる状態にする。利用者が録音前に何が送られるかを知り、後から自分の
データを消せる条件を、実装前に仕様として確定する。

## 7. 採用した方針（2026-09-28）

判断の経緯と理由は§25、比較は§18–§21を参照する。

1. 音声は実サービスへ送る。経路は同一originのRails経由（multipart）で、Railsが認証・所有者・形式・
   sizeを検証する。**音声原本を長期保存しない。**ただし**処理が終わるまでの一時的な預かりとして
   S3東京へ置く**（§18案A2）。**Dotの保存まで通ったら**即削除し、失敗した場合は受理から24時間を再試行の
   期限として、期限が来たら**アプリが削除する**（S3のlifecycleは取りこぼし用の保険で、24時間の
   根拠にはしない）。Dotの削除・退会の時点で残っていれば消す。presigned URLとCORSは使わない。
   uploadより後の再試行・Job実行・削除を認可するため、**処理ID・所有者・key・期限をserverが記録する。**
2. **文字起こし全文をRDSへ保存しない。**代わりに、話した内容の**要約（`summary`）をDotと同じ行に
   1件保存する。**
3. **Dotとして残すのは`sentence`（今日の一文）と`summary`（話した内容の要約）。**`reflection`と
   `closing`は生成も保存もしない。保存するのは利用者が整理した内容であり、AIからの語りかけは残さない。
4. 端末では、文字起こし全文を**`sessionStorage`にタブを閉じるまで**保持する。localStorageへの
   永続化はしない。そのためresponseには文字起こしを含める。
5. 削除は**Dotの個別削除と退会の両方**をMVPに入れる。物理削除とし、削除できなかったときに削除済みと
   表示しない。
6. **生成結果の編集は持たない。**訂正手段は削除して録り直すこととし、journalingの「更新」の表現を
   これに合わせる。
7. 録音前（認証確認の後、マイク起動の前）に、送信先・音声を一時的に預かって消すこと・残るもの・
   削除できること・他人の実名は言い換えられること・外部へ渡った内容の即時削除は保証できないことを
   知らせる（§22）。
8. 端末の既存`fod.session.v1`は、実サービス化の変更で読み取りをやめ、起動時に削除する（§22）。

## 8. Why This Approach

- privacy.md §2原則1（データを減らす）と§4の初期案（音声原本の長期保存と全文文字起こしの保存は
  避ける方向で比較する）に沿う。音声原本の長期保存と文字起こし全文の保存をしないと確定するため、
  以後「未決定なのに保存しないと説明する」状態がなくなる。
- **長く残るものをDot 1行に収める。**削除連鎖・孤児データの回収という運用が最小になる。要約もDotと
  同じ行にあるため、Dotを消せば必ず一緒に消える。音声だけがRDSの外にあるので、そこは期限での削除と
  削除連鎖を別に設計する。ECS 1タスク・Single-AZという現在の小さな構成（architecture）と釣り合う。
- 認証・所有者判定・size検証・破棄をRailsの一箇所に置けるため、「誰の音声か」の判定とCSRF・Cookieの
  扱いをTASK-001の採用（同一origin・CookieStore）から変えずに済む。
- 残す対象を「利用者が整理した内容」に絞ることで、保存の目的が説明できるものだけになる。AIの語りかけ
  （`reflection` / `closing`）は読み返す目的が弱く、保存すれば個人的な文面が増えるだけになる。
- 音声は処理が終わるまでの一時的な預かりに限る。録音を30分まで許す以上、生成に失敗したら30分話した
  内容を捨てて録り直す、という体験は成立しない。一方で、成功したら即削除し、失敗しても24時間で
  預かりを終わらせることで「長期保存しない」という制約は守れる。画面の文言と実際の保持・再試行を
  同じ変更で一致させ、**保証できない期限を約束しない**（§22、TASK-010/011）。

## 9. Data Flow（採用内容）

```text
[録音前]
Home / /record 直アクセス
  → Railsで認証・メール確認・7日期限を確認（journaling「録音前認証」）
  → 送信内容と残るもの・削除できることを知らせる案内を表示
  → 利用者が了解して初めて getUserMedia（マイク起動）

[録音〜送信]
MediaRecorder（browser memory のみ。音声を storage へ書かない）
  → 停止（最長30分 / 上限到達で自動停止。audioBitsPerSecond は 32000 を明示）
  → POST /api/v1/dots（同一origin・multipart・Cookie + CSRF）★音声が端末を出る境界
       ↓ Rails: 認証再確認 → 所有者決定 → content type と size を検証
       → S3東京へ一時object（非公開・暗号化・versioning無効・keyはUUID）
          ＋ 処理の記録（処理ID・所有者・key・受理時刻・再試行期限・状態）★認可の根拠はこの記録
       → 外部文字起こしへ送信              ★★元音声が外部（第三者）へ渡る最初の境界
       → 文字起こしテキスト（memory のみ。DB へ書かない）
       → 外部AIへ送信                      ★★★発話内容が生成AIへ渡る境界
       → sentence と summary を生成し、Dot として RDS 東京へ保存（user_id で所有者を固定）
       → 成功（＝Dot の保存まで完了）: S3 の一時object を即削除
               （記録をいつ消すかは TASK-003 と相互確認）
       → 失敗: object を残し、受理から24時間は同じ音声で再試行できる
               （再試行は記録の所有者と current_user の一致を確認する）
               期限が来たらアプリが削除する。lifecycle は落ちたときの保険
  → response は Dot（sentence / summary / date / durationSec）と文字起こし全文
       ↓ 端末: 文字起こしは sessionStorage（タブを閉じるまで）。localStorage へ書かない
       → /dot で sentence、/reflection で summary と文字起こしを表示

[保存後]
RDS dots（正本: sentence / summary / date / duration） ─ 参照は current_user.dots scope
  → 個別削除: そのDotを作った処理の一時object が残っていれば先に消し、次に dots の行を消す
              （他の録音の一時object には触れない）
  → 退会: 新規の保存・再試行・結果の確定を止めてから、その利用者の一時object と記録を
          すべて消し、user と dots を削除する。あとから現れた分を回収するまで完了としない。
          session を破棄、sessionStorage を消す
  → S3 の削除に失敗したら、削除済みと表示せず再実行する
  ※ 外部provider側に渡った内容の即時削除は保証しない（利用者へ説明する）
  ※ RDS 自動backup の保持期間内は削除済みデータが backup に残る

[保持しないもの]
音声原本: 長期保存しない。成功時は即削除、失敗時も受理から24時間でアプリが削除する。
          RDS へは入れず、端末の storage へも書かない
文字起こし全文: RDS に保存しない（列を作らない、ログに出さない）。端末はタブを閉じるまで
reflection / closing: 生成も保存もしない
```

★の3点が、privacy.md §2原則2が「データフローに示す」ことを求めている境界である。★★以降は
Focus on Dot側で削除しても委託先に残り得るため、録音前の案内に含める（§22）。

## 11. Libraries / APIs

本Planでは新しいdependencyを追加しない。決定が前提とする既存のものは次のとおり。

- MediaRecorder（既存）: 記録形式がbrowser既定に依存するため、serverが受容する形式を列挙する必要がある。
- `sessionStorage`（Web標準）: 文字起こしのタブ内一時保持に使う。localStorageと違いタブを閉じると
  消えるため、端末に残り続けない。新しいlibraryを入れずに要件を満たせる。
- Rails multipart（`ActionDispatch::Http::UploadedFile`）: 音声を受け取り、S3へ渡した後は明示的に
  削除する。ECSのローカルdiskを正本にしない方針（architecture）と矛盾しない使い方に限る。
- S3（東京）+ lifecycle: 処理が終わるまでの一時的な預かり場所。非同期にすると受信したcontainerと
  Jobを実行するcontainerが同じとは限らず、deployでも入れ替わるため、ECSのローカルdiskを受け渡しに
  使えない。lifecycleの期限切れ削除は追加のコードなしで「置きっぱなしにしない」を担保できる。
  **presigned URLとCORSは使わない**（§18案A2）。AWS SDK for Rubyの導入がTASK-009で必要になる。

## 13. Risks / Things to Watch

- **「保存しない」と「一時的に預かる」の説明の差。** 音声は受理から24時間はS3に存在し、障害時には
  それより長く残り得る。録音前の案内で「保存しません」と言い切ると事実と違う。現行ErrorStateの
  「音声は保存されています」も、一時的な預かりを恒久的な保存と誤解させ得る。**利用者へ約束するのは
  「やり直せる期限」だけにし、「消える期限」を約束しない**（§22、TASK-010/011）。
- **一時objectの消し残り。** 成功時の削除と期限での削除はアプリが行うため、Jobの停止・例外・
  deployの入れ替わりで落ちると残る。lifecycleは保険だが**削除完了の期限を保証しない**
  （下記）。削除の失敗と残存を検知できるようにし、bucket設定そのものも検証対象にする（TASK-013/015）。
- **削除したつもりで実体が残る設定。** S3のversioningが有効だと、`DeleteObject`もlifecycleの
  expirationもdelete markerを付けるだけで、音声の実体はnoncurrent versionとして残る。
  **「削除した」という操作が成功しても、消えたことにならない。**versioningを有効にしない方針を
  採るが（§18案A2の条件）、設定は構築時に確認しないと保証にならない。同種の落とし穴として、
  bucketのreplication・backup・object lockが有効だと、別の場所や別の期間で残り得る。
- **lifecycleに削除完了の上限はない。** AWSのlifecycleは日数指定の期限を翌日のUTC 0時へ切り上げる
  ため、`Days: 1`でもobjectが**削除対象になる**のは作成から約24〜48時間後である。さらにその後の
  削除は非同期に行われ、遅延し得る。**約48時間は「削除対象になるまで」の目安であって、削除が
  完了する上限ではない。**lifecycleを根拠に「◯時間で消える」と文書にも画面にも書かない。
  24時間の誤った保証を48時間の保証へ置き換えない。
- **保存済みobjectの認可。** 推測困難なkeyは秘密であって所有権ではない。再試行・Job実行・退会時の
  削除は、server側の記録で所有者を照合する。照合しないと、処理IDやkeyを知っていれば他人の音声を
  再処理・取得できる経路が生まれ得る。
- **外部へ渡った内容は消せない。** Dotを削除しても、委託先の保持期間内は入力が残り得る。
  「削除しました」の表示範囲を自分たちのデータに限って書く必要がある。
- **backupからの復活。** 障害復旧でRDSを復元すると、削除済みのDotが戻り得る。復元手順に削除要求の
  再適用を含めないと、消したはずのデータが再出現する。
- **一時ファイルの取りこぼし。** 例外・タイムアウト・タスク終了で一時ファイルが残る経路がある。
  ensureでの削除に加え、TTLでの強制削除と、残存の検知方法が必要。
- **文字起こしをresponseに含めること。** 端末へ渡すため、responseとclient側の扱いが増える。
  ログ・error trackingのrequest/response記録に本文が乗らないこと、`sessionStorage`がlogoutと
  User切替で消えることを実装時に確認する（TASK-011/014/015）。
- **要約の品質と個人情報。** 要約にも第三者の実名が残り得る。要約だから安全とは扱わず、Dot本文と
  同じ保護・削除・説明の対象にする。要約のpromptと粒度はTASK-003。
- **録音形式のbrowser差。** Chrome系のwebm/opusとSafariのmp4/aacで、外部文字起こしの受容形式が
  異なる可能性がある。TASK-003で確認しないまま上限や形式を実装すると、Safariだけ失敗し得る。
- **ログへの流入。** 例外のbacktraceやrequestのdumpに音声のファイル名・文字起こし・Dot本文が
  混ざる経路がある。既定で本文をログへ出さない設定と、例外時の出力範囲を確認する。
- **端末の旧データ。** `fod.session.v1`はmockと実データを区別しておらず、共有端末では別Userに
  前の利用者のDotが見える。実サービス化の変更で確実に破棄する必要がある。
- **`reflection` / `closing`の廃止。** 現行のschema・mock・`/reflection`画面・testが前提にしている。
  削除は表示と契約を同時に変える変更として行う（TASK-005/011）。本Planではコードを変更しない。

## 18. 判断1: 音声の経路と原本保存（比較。採用は§25-1）

**採用は案A2（案Aと案Bの中間）。**当初は案Aを採ったが、録音の上限を30分にしたことで「失敗したら
録り直し」の負担が重くなり、案A2へ変更した（§25-9）。

### 案A（不採用）: Rails経由で送り、原本は保存しない

- 経路: Browser →（同一origin・multipart・Cookie + CSRF）→ Rails → 外部文字起こし → 外部AI → RDS。
  音声はRailsの一時ファイルとしてのみ存在し、成否にかかわらず削除する。
- 利点: 保存物がDotだけになる。認証・所有者決定・形式とsizeの検証・破棄をRailsの一箇所に置ける。
  S3のbucket・暗号化・lifecycle・アクセス制御・削除連鎖・孤児objectの回収が不要。追加の保存費が
  発生しない。privacy.md §2原則1と§4の初期案に沿う。
- 欠点: 生成失敗時に音声が残っていないため、利用者は録り直しになる。upload中はPumaのworkerが
  占有される（30分・32MBまで許すため、上り1Mbpsなら約4分。実測が必要）。ErrorStateの文言を変更する必要がある。

### 案A2（採用）: Rails経由でS3東京へ一時的に預かり、失敗したら同じ音声を再処理する

- 経路: Browser →（同一origin・multipart・Cookie + CSRF）→ Rails → **S3東京へ一時object** →
  文字起こし → 外部AI → RDS。**Dotの保存まで通った時点**でobjectを削除し、失敗した場合は24時間だけ預かって
  アプリが削除する。
- 案Aとの違いはS3へ置くこと、案Bとの違いはpresigned URLとCORSを使わないことだけである。
- **S3が必要な理由は再試行だけではない。**30分の音声は同期HTTPで処理しきれず非同期になるため
  （§18の「30分にしたことの帰結」）、requestを受け取ったcontainerとJobを実行するcontainerが同じとは
  限らない。deployでも入れ替わる。ECSのローカルdiskを受け渡しに使えないので、一時的な置き場が要る。
- 利点: 生成・保存の失敗やJob再実行で録り直しが要らない。**uploadを受け付ける時点の**所有者は
  requestの`current_user`で確定するため、presigned URLを発行せずに済み、発行範囲の誤りで他人の
  objectへ到達する経路が生まれない。CORSも不要。
  **ただし、uploadより後（再試行・Job実行・削除）の認可には所有者の記録が要る**（下記の条件）。
- 欠点: uploadの間はPumaのthreadを占有する（本リポジトリは`RAILS_MAX_THREADS`既定3・1プロセス・
  ECS 1タスクなので、長いuploadが3本重なると他のrequestが待たされる）。S3のbucket・暗号化・
  lifecycle・削除連鎖・孤児objectの回収は案Bと同じだけ必要になる。
- 実測してPuma占有が問題になれば、bucketとlifecycleをそのまま使って案B（presignedの直接upload）へ
  移せる。先に大きい仕組みを入れず、順に寄せる。

### 案A2の一時保存の条件（採用）

- bucketは非公開（public access block）、保存時に暗号化する。keyは推測不能なUUIDにし、user_idや
  日付など推測できる値を含めない。
- **bucketのversioningを有効にしない（採用）。**versioningが有効だと、通常の`DeleteObject`も
  lifecycleのexpirationも**現行versionにdelete markerを付けるだけ**で、音声の実体はnoncurrent
  versionとして残る。「成功したら即削除」も「期限が来たらアプリが削除」も「lifecycleが保険として
  最後には消す」も、いずれも**versioningが無効であることを前提にした記述である。**
  一時的な預かり用のbucketに復元性は要らないため、有効にしない。
  - 監査・ransomware対策など他の理由でversioningを有効にする場合は、次をセットで必須とする。
    有効化だけして削除ルールを足さない状態を作らない。
    1. noncurrent versionのexpiration（例: 1日）を設定する。
    2. 期限切れのdelete markerを削除するルールを設定する。
    3. アプリの削除も、delete markerを付けるだけで終わらせず、実体が消える方法で行う。
  - **versioningの設定は、この方針が成立するかどうかを決める前提条件である。**構築時に設定を
    確認し、検証対象に含める（TASK-009/015）。「既定では無効だから大丈夫」と仮定しない。
- **server側に処理単位の記録を持つ。**最低限、処理ID・所有者（user_id）・object key・受理時刻・
  再試行できる期限・状態を持つ。**推測困難なkeyを所有権の代わりにしない。**
  - uploadを受け付けた時点の所有者はrequestの`current_user`で決める。clientから渡されたkeyや
    user_idを信用しない。
  - **uploadより後の操作はこの記録で認可する。**別requestでの再試行、別containerで動くJob、
    退会時の削除は、いずれも「そのobjectが誰のものか」を初回requestの外で判断する必要がある。
    再試行では要求元の`current_user`と記録の所有者が一致することを必ず確かめる。
  - 記録の置き場所（RDSの表かどうか）と項目の確定はTASK-003/005へ渡す。TASK-002は
    「所有者・key・期限をserverが持ち、再試行時に所有者を照合する」ことを必須条件として置く。
  - **記録自体も個人データである**（誰がいつ録音したかが分かる）。§17に行を設け、保持と削除の
    対象に含める。削除に失敗して回収が要る間は、回収に必要な記録を消さない。
  - **成功した処理の記録をいつ消すかは、ここで固定しない。**応答喪失後の結果照会や冪等性の判定に
    必要なら残す必要があるため、TASK-003の同期/非同期と冪等性の決定と相互確認する。音声objectは
    成功時に即削除する（こちらは確定）。
- **「成功」の定義:** 本Planで音声を削除する契機として使う「成功」は、**DotがRDSへ保存されるまで
  完了したこと**を指す。文字起こしが通ったこと、生成が通ったことではない。文字起こしや生成だけ
  通った時点で音声を消すと、その後の保存で落ちたときに24時間の再試行が録り直しなしには成立しない。
  §22の失敗時の表のとおり、**保存（RDS）の失敗でも音声は残す。**
- **再試行できる期限は受理から24時間。**期限を過ぎた再試行は受け付けず、録り直しを案内する。
- **物理削除はアプリが行う。**Dotの保存まで通った時点で即削除し、期限（24時間）が来たものは定期実行で
  削除する。削除に失敗したら再実行し、**消えずに残っているobjectを検知できるようにする**。
- **S3のlifecycleは保険であり、削除時刻の根拠にしない。**`Days: 1`でもobjectが削除対象になるのは
  期限が翌日のUTC 0時へ切り上げられるため作成から約24〜48時間後で、その後の削除も非同期に行われる。
  **削除が完了する時刻に上限はない。**lifecycleはアプリの削除が落ちたときに最終的には消えることを
  担保する目的だけに使い、「いつまでに消える」の根拠にはしない。
  なお**この「最終的には消える」もversioningが無効であることが前提**で、有効なら上記の追加ルールが
  ないとnoncurrent versionとして残り続ける。
- **利用者への説明は保証できる範囲に揃える。**約束するのは**やり直せる期限（受理から24時間）**で
  あって、消える期限ではない。「Dotができた時点、または期限のあとに削除する」「障害時には削除が
  遅れる場合がある」と伝え、「必ず◯時間以内に消える」とは言わない（§22）。
- Dotの削除・退会の時点で残っていれば消す。削除の範囲は§20のとおり、個別削除と退会で分ける。
- 障害調査のためにobjectを人が取り出すことを常用の運用にしない。取り出す場合の条件はTASK-015/017で扱う。

### 案B: presigned URLでS3東京へ直接uploadする（今回は採用しない）

- 経路: Browserがpresigned URLでS3へ直接upload → RailsがJobで取得 → 文字起こし → AI → RDS。
  objectの削除は案A2と同じ条件（成功時は即削除、失敗時は受理から24時間でアプリが削除、lifecycleは保険）。
- 利点: 生成・保存の失敗やJob再実行で録り直しが要らない。障害調査で実際の入力を確認できる。
  Railsのupload占有が短い。
- 利点: 案A2の利点に加えて、Pumaのthreadを占有しない。
- 欠点: presigned URLの発行範囲を誤ると他人のobjectへ到達し得るため、**発行したUserとkeyの対応を
  serverが持つ記録**（短命の`audio_uploads`相当）と、その検証が必要になる。browserから直接PUTする
  ためbucketにCORSも要る。clientが2段階（presigned取得 → PUT → 生成依頼）になり、失敗の組合せが増える。
- 費用はS3側の実費が案A2と同じでほぼゼロ。差は実装と検証の量である。Puma占有が実測で問題になった
  時点で移す。

### 案C: 音声を外部へ送らず、端末内で文字起こししてテキストだけ送る（今回は採用しない）

- Web Speech APIは既定ではサーバー側の認識に委ねられ得るため、何もしなければ音声がブラウザ事業者へ
  渡る。一方で仕様には**端末内処理を要求する`processLocally`と、端末内で利用できるかを確認する
  APIがある。**したがって「端末内で完結する手段は存在しない」とは言えない。
- **未確認なのは、成立する範囲である。**対応ブラウザ・対応OS、日本語での可用性、30分の連続録音での
  品質と安定性、失敗時のfallback（結局サーバー側へ渡る経路に戻らないか）を、一次資料と実機で
  確かめていない。端末内モデル（Whisper WASM等）はモデルのdownloadが数十〜数百MB規模で、mobileでの
  実行時間・電池・精度が課題になる。
- **採否の判断: MVPでは採用しない。**理由は成立しないからではなく、**対応範囲と検証コストが
  MVPの規模に見合わないため**である。採用するなら、上記を確かめたうえで、端末内で処理できない
  環境へのfallbackをどうするかも同時に決める必要がある。
- 採用しない結果として、**固有名詞を含む元音声は外部の文字起こしへ渡る。**これはprivacy.md §2原則2が
  「明示する」よう求めている事実であり、利用者に説明する（§22）。「端末内では不可能だから」ではなく
  「今回は採らなかったから」である、と説明の根拠を取り違えない。
- 再検討の条件: 対応ブラウザでの端末内認識が日本語・長時間で実用になると確認できたとき。
  TASK-003が固有名詞の低減手段を検討する際に、この案も選択肢として再評価する。

### 送信仕様（採用）

- 経路: 同一originの`POST /api/v1/dots`（`multipart/form-data`）。認証Cookieとcsrf tokenを検証し、
  所有者はserverのcurrent_userで決める。clientのuser_idを信用しない。正式な契約はTASK-005。
- 形式: 現行は`new MediaRecorder(stream)`でmimeType未指定のため、Chrome系は`audio/webm;codecs=opus`、
  Safariは`audio/mp4`が一般的である。serverは受容するcontent typeを列挙して検証し、非対応なら
  保存も外部送信もせず録り直しを案内する。外部文字起こしが受け付ける形式はTASK-003で確認する。
- 上限: 録音は**最長30分**とし、到達時は自動停止してその時点までを送る。requestの上限は**32MB**。
- bitrate: `MediaRecorder`に`audioBitsPerSecond: 32000`を明示する。browser既定に任せない。
  音声だけの用途では32kbpsで足り、30分でも約7.2MBに収まる（32kbps = 4KB/s × 1800秒）。
  `audioBitsPerSecond`はhintであり従わないbrowserがあり得るため、既定寄りの128kbpsで30分＝約28.8MBに
  なる場合でも受け取れるよう、serverの上限は32MBとする。**上限を7〜10MBに絞ると、hintが効かない
  browserで30分話した録音が送信時に丸ごと失われる。**それを避けるための32MBである。
- 端末側の事前確認: 停止時に`blob.size`を確認し、上限を超えていれば送信せずに知らせる。serverも
  上限超過を拒否し、その場合は音声を外部へ送らない。
- responseに音声のURLを含めない。文字起こしは§25-4のとおり含める。

### 30分にしたことの帰結（2026-09-28の上限変更で追加）

- **同期HTTPで完結させるのは成立しない見込み。**30分の音声の文字起こしは実時間より短いとはいえ
  分単位を要し、ALBのidle timeoutは既定60秒である。TASK-003は**非同期前提**で検討する必要がある。
  非同期にすると、requestを受けたcontainerとJobを実行するcontainerが同じとは限らないため、音声の
  受け渡し場所が要る。これも案A2を採る理由になる（§18案A2）。
- **Pumaの占有時間が延びる。**32MBを上り1Mbpsで送ると約4分かかる。ECS 1タスクという現在の構成では、
  同時に数件の長いuploadが重なるとアプリが詰まり得る。実測し、成立しないなら§18案B（S3への
  一時的な直接upload。lifecycleで即時削除し、原本の長期保存はしない）へ切り替える条件を決める。
- **録り直しの負担が重くなる。**5分なら「失敗したら録り直し」は受け入れられるが、30分話した後に
  生成が失敗して録り直しになるのは負担が大きい。これが決め手となり、案Aから案A2へ変更した（§25-9）。

## 20. 判断3: 削除要求の受け付け方（比較。採用は§25-5）

- **案A（採用）: Dotの個別削除と退会（アカウント削除）の両方をMVPに入れる。**
- 案B: 退会のみ。個別削除は将来。
- 案C: 個別削除のみ。退会は問い合わせでの運用対応。

判断の材料:

- journaling.md §4は「保存されたDotは認証済み利用者本人だけが取得・更新・削除できる」をMVP受け入れ
  条件に既に含め、TASK-013が削除と残存の検証を担当する。案Aが現行仕様と整合する。
- 案Bだけでは「1件だけ消したい（他人の実名を言ってしまった）」に応えられず、privacy.md §2原則5の

  個別削除がないと訂正手段が退会だけになる。
- 案Cは「全部消したい」に自動で応えられず、運用の手作業と本人確認の手順が増える。

### 削除仕様（採用）

- **Dotの個別削除:** `dots`の行を物理削除する。論理削除にしない（残す目的がなく、privacy.md §2原則1に
  反する）。`sentence`と`summary`は同じ行なので同時に消える。文字起こし全文はserverに存在しない。
  音声は、そのDotを作った処理の一時objectが残っていれば一緒に消す（生成に成功していれば既に
  削除済みなので、通常は対象がない）。**その利用者の他の一時objectには触れない。**
  別タブで生成中のものや、失敗して再試行を待っているものまで消すと、24時間の再試行ができなくなる。
- **退会:** userとそれに属するdots、認証情報、**その利用者の一時objectと処理の記録すべて**を削除し、
  sessionを破棄する。端末の`sessionStorage`も消す。コピー済みCookieの即時失効は保証しない
  （architecture既記載）。
- **退会と進行中の処理の競合（必須条件）:** 対象を数えて消すだけでは足りない。退会より前に認証を
  通過したuploadが、退会側の列挙・削除のあとにS3への保存を終えると、記録が消えた後に音声だけが
  残る。S3から音声を読み出し済みのJobは、objectを消しても止まらず、生成結果を書き込み得る。
  TASK-002としては次を必須条件とする。
  - **退会処理と競合する新規の保存・再試行・生成結果の確定を防ぐ。**退会を受け付けた時点以降、
    その利用者の新しいuploadと再試行を受理せず、進行中の処理の結果を確定させない。
  - **受理済み処理の残存を回収するまで削除を完了としない。**列挙して消した後に現れたobjectや
    記録を拾い直し、すべて消えたことを確認してから完了を表示する。
  - 具体的な状態遷移と排他の方式（状態列で弾くか、退会を非同期の完了待ちにするか等）は
    **TASK-003/005**で決め、実装と検証は**TASK-009/013/015**で行う。
  - これは「生成のcancel UIを持つか」とは別の話である。cancelはMVPで持たない（下記）が、
    退会時に結果が後から確定しないことは持たなければならない。
  - TASK-001 Planの「受理済み処理の所有者は変更しない」「logoutはJob取消しではない」と整合させる。
    退会はlogoutと違い、**受理済み処理を残したまま終われない。**
- **外部provider側:** Focus on Dot側の削除は委託先のデータを消さない。委託先の保持期間内は入力が
  残り得ることを削除時の表示と録音前の案内に含め、「完全に削除しました」と書かない。
- **backup:** RDS自動backupの保持期間内は、削除済みのDotがbackupに残る。障害復旧で復元した場合に
  削除済みデータが再出現し得るため、復元手順に「復元後の削除要求の再適用」を含める（TASK-013/015へ引継ぎ）。
- **生成中の削除:** Dotの行がまだないため、削除対象が存在しない。MVPでは進行中の処理を止める操作を
  持たず、生成が終わってDotができた後に本人が削除する。TASK-003が非同期生成を採る場合は、待ち時間の
  長さに応じてcancelの要否をそちらで再判断する。
- **削除の順序と部分失敗:** RDSとS3にまたがるため、単一のtransactionで完結しない。**先にS3の
  一時objectを消し、成功してからRDSの行と処理の記録を消す。**逆順にすると、記録を消した後にS3の
  削除が失敗したとき、どのobjectが誰のものか分からなくなって消し残る。
  - S3の削除に失敗したら、その削除要求全体を失敗として扱い、**削除済みと表示しない。**
  - 失敗は記録に残し、再実行できるようにする。lifecycleは保険として働くが、それを理由に
    「消えたことにする」表示をしない。
  - 退会のように複数のobjectを消す場合は、どこまで消えたかを記録し、残りを再実行する。
    一部だけ消えた状態で「すべて削除しました」と表示しない。
- **削除の失敗:** 失敗時は削除済みと表示せず、失敗した旨と再実行の手段を示す
  （privacy.md §2原則5の「誤った完了表示」を避ける）。実装と検証はTASK-013/015。
- **削除の認可:** `current_user.dots.find`相当で本人のDotに限る。他人のIDを指定しても存在しない扱いに
  する。一時objectも同じで、server側の記録の所有者と`current_user`が一致するものだけを対象にする。
  keyや処理IDを知っていることを権限の根拠にしない。

## 22. 保持期間・ログ・説明の既定（採用）

### 保持期間

- Dot（`sentence` / `summary` / `date` / `duration`）: 本人が削除するか退会するまで。期間による
  自動削除はしない（振り返りが目的のため）。
- 音声（server側）: S3東京の一時object。**DotがRDSへ保存されるまで完了した時点**で即削除。失敗時は**受理から24時間**を
  再試行できる期限とし、期限が来たらアプリが削除する。Dot削除・退会の時点で残っていれば削除する
  （範囲は§20）。**S3のlifecycleは保険であり、24時間の根拠にしない**（`Days: 1`でも翌日のUTC 0時へ
  切り上げられ、削除対象になるのが作成から約24〜48時間後、その後の削除も非同期で完了の上限がない）。
- 文字起こし（server側）: 処理中のmemoryのみ。DBにもS3にも書かない。
- 文字起こし（端末側）: `sessionStorage`でタブを閉じるまで。logoutとUser切替でも削除する。
- ログ: 既定14日。RDS自動backup: 既定7日。いずれもarchitectureの「backup保持/復元目標」「監視の
  具体値」が未決定のままなので、公開前に実値を確定する。

### ログに出さないもの

音声（内容・ファイル名）、文字起こし、Dotの`sentence`・`summary`、Cookie・session値、Google callbackの
code、確認・再設定token、メール本文。出すのはuser_id・dot_id・処理段階・結果・所要時間まで。ALB access
logは初期無効（architecture既記載）。例外のbacktraceやrequest dumpに本文が混ざらないことを実装時に確認する。

### 録音前に知らせる内容

認証確認の後、マイク起動の前に次を示す（journaling.md §4の受け入れ条件と「録音前認証」に整合）。

1. 音声を実サービスへ送ること。自分たちのserverを経由して、外部の文字起こしとAIへ渡ること。
2. 音声を預かること、**やり直せるのは受け付けから24時間**であること、**成功した時点または期限の
   あとに削除すること**、**障害時には削除が遅れる場合がある**こと。
   例:「録音は、Dotを作るあいだだけお預かりします。うまくいかなかったときは、受け付けから24時間は
   やり直せます。Dotができた時点、または期限を過ぎたあとに削除します。障害が起きたときは削除が
   遅れることがあります。」
   **約束するのは「やり直せる期限」であって「消える期限」ではない。**
   「保存しません」「必ず24時間以内に消えます」「48時間以内に消えます」はいずれも書かない。
   前者は事実と違い、後の2つは削除の完了時刻を保証できない設計に対して強すぎる（§18案A2の条件）。
3. 音声と文字起こし全文を残さず、残るのは今日の一文と話した内容の要約であること。
   文字起こしはタブを閉じるまでの間だけ端末で見られること。
4. Dotは本人だけが見られ、1件ずつ削除でき、退会ですべて消せること。
5. 他人の実名・住所・連絡先は、必要がなければ言い換えられること。
6. 外部へ渡った内容の即時削除は保証できないこと。
7. 固有名詞の置換を行う場合でも見逃しがあるため、「匿名化済み」とは言わないこと（置換の採否はTASK-003）。

### 失敗後に実際に残るデータと再送可否

| 失敗・中断の起点 | 端末 | S3の一時object | RDS | 外部 | 再送 |
| --- | --- | --- | --- | --- | --- |
| 録音中に離脱・タブを閉じる | 何も残らない（memoryのみ） | なし | なし | なし | 不可（録り直し） |
| 権限拒否・非対応 | なし | なし | なし | なし | — |
| 送信失敗（network） | memoryのBlobのみ（画面に留まっている間） | なし | なし | なし | 同じBlobで再試行できる |
| 送信時に認証失効 | memoryのBlobのみ | なし | なし | なし | 再ログイン後、同一Userなら再試行できる。別Userへ入り直した場合は送らない |
| 文字起こし・AIの失敗 | なし | **残る（24時間）** | なし | **音声が渡った事実は残る** | **録り直さずに同じ音声で再試行できる** |
| 保存（RDS）の失敗 | なし | **残る（24時間）** | なし | 音声・テキストが渡り、生成は消費済み | **同じ音声で再試行できる。**ただし外部AIの消費は繰り返される |
| 生成成功後に応答が届かない | 文字起こしも届かない | 削除済み（成功しているため） | Dotが存在し得る | 渡り済み | 再試行せず、一覧で結果を確認できるようにする（冪等性の手段はTASK-003） |
| 再試行しないまま24時間が過ぎる | なし | **アプリが削除する** | なし | 渡り済み | 不可（録り直し） |

現行ErrorStateの「音声は保存されています。もう一度試してください。」は、案A2では**再試行できる点は
合うが、「保存されている」という言い方が24時間の預かりを恒久的な保存と誤解させ得る**。
次の条件で文言を変える（journaling.md §3の差異解消、TASK-010/011で表示と実挙動を同時に変える）。

- **音声が残っていて再試行できる状態のときだけ**、やり直せる旨を表示する。送信前の失敗や期限切れで
  同じ音声を使えない場合に「お預かりしています」と出さない。
- **期限は相対時間で書かず、serverが返した期限日時を表示する。**「24時間以内ならやり直せます」は
  起点が伝わらず、受理から23時間後に再び失敗した画面でも「まだ24時間ある」と誤解させる。
  serverは処理の記録が持つ再試行期限を返し、clientはそれを表示する（契約はTASK-005）。
- **消去の期限を約束しない。**「24時間で消えます」「48時間で消えます」とは書かない。
- 例:「録音をお預かりしています。◯月◯日◯時までやり直せます。」

### 端末の既存`fod.session.v1`

実サービス化の変更で、このkeyの読み取りをやめ、起動時に`removeItem`して破棄する。Dotの正本をRDSにし、
localStorageへ新しい永続keyを作らない。表示のcacheが必要になった場合も本人性の根拠にしない。
理由は、旧keyがmockと実データを区別しておらず、共有端末では別Userに前の利用者のDotが見えるためである。
TASK-010/014へ引き継ぐ。

### 10. 別AIのレビューを受けて直した点（2026-09-28）

Planと反映先をCodexにレビューしてもらい、次の5点を修正した。いずれも指摘が妥当だった。

1. **lifecycleを「24時間で消える」根拠にしていた。**AWSのlifecycleは日数指定の期限を翌日のUTC 0時へ
   切り上げ、削除も非同期である。`Days: 1`でも削除対象になるのは約24〜48時間後で、完了の上限はない。**再試行の期限（24時間）と物理
   削除を分け、削除はアプリが行い、lifecycleは保険**という設計に改めた。利用者への説明も、消去の
   期限を約束しない形に変えた。
2. **「presignedを使わないから所有者の記録は要らない」は誤りだった。**presignedを使わないことで
   なくせるのは発行範囲の誤りだけで、別requestでの再試行、別containerでのJob実行、退会時の削除は、
   いずれも初回requestの外で所有者を判断する。**処理ID・所有者・key・期限の記録と、再試行時の所有者
   照合を必須条件**として追加した。推測困難なkeyを所有権の代わりにしない。
3. **§20の削除仕様に案A（保存しない）の前提が残っていた。**「音声はserverに存在しない」「単一のRDS
   transactionで完結する」を、**S3を含む削除順序・部分失敗の扱い・再実行・完了表示の条件**へ
   書き換えた。先にS3を消してからRDSを消す。
4. **Dot個別削除が、その利用者の別の録音まで消す記述になっていた。**個別削除は対象Dotに紐づくobject
   だけ、退会は本人の全object、と範囲を分けた。別タブで生成中・再試行待ちの録音を巻き込まない。
5. **端末内文字起こしが「成立しない」という結論が根拠より強かった。**Web Speech APIには端末内処理を
   要求する`processLocally`がある。**「成立しないから採らない」ではなく「対応範囲と検証コストが
   MVPに見合わないから今回は採らない」**へ書き換え、再検討の条件を残した。

### 12. 3回目のレビューを受けて直した点（2026-09-28）

3巡目で「前回の4件は解消。文書間の食い違いもなし」と確認されたうえで、新しい指摘を1件受けた。

**S3のversioningが有効だと、削除しても音声の実体が残る。**versioningが有効なbucketでは、通常の
`DeleteObject`もlifecycleのexpirationも現行versionにdelete markerを付けるだけで、実体は
noncurrent versionとして残る。つまり「成功したら即削除」「期限が来たらアプリが削除」
「lifecycleが最後には消す」は、**いずれもversioningが無効であることを暗黙の前提にしていた。**
削除操作が成功を返しても消えていない、という状態が起き得る。

対応として、**versioningを有効にしない**ことを§18案A2の条件に加えた。一時的な預かり用のbucketに
復元性は要らない。他の理由で有効にする場合は、noncurrent versionのexpiration、期限切れdelete
markerの削除、実体が消える削除方法の3つをセットで必須とし、有効化だけして削除ルールを足さない
状態を作らない。設定の確認はTASK-009（構築）とTASK-015（検証）の対象にした。

同種の落とし穴（replication・backup・object lock）も§13へ書き添えた。設定で「削除した」の意味が
変わる仕組みは、方針の前提条件として明示しないと保証にならない。

§22の既定（保持期間・ログ・録音前の説明・失敗時の残存・旧`fod.session.v1`）は質問にせず、採用内容に
合わせて確定した。音声の保持は、当初の「処理直後に削除・TTL 15分」から「成功時は即削除、失敗時は
受理から24時間でアプリが削除」へ変えた。24時間は、利用者が失敗に気づいて再試行するまでの現実的な
猶予として置いた値で、**実測根拠はない。**短縮の判断材料（実際の再試行までの時間、期限切れで
録り直しになった件数）を運用で取り、短くできるなら短くする。
