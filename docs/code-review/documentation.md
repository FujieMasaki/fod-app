# 仕様・設計文書 AIコードレビュー指針

仕様・設計文書・レビュー指針・タスク・Planの変更をレビューするときの観点を定める。**対象は`docs/`配下
（`docs/tasks/`・`docs/implementation-plans/`・`docs/code-review/`・`docs/development/`を含む）だけでなく、
`AGENTS.md`・`CLAUDE.md`・`README.md`・`contracts/README.md`等のルートの文書と、
`.claude/agents/*.md`・`.claude/skills/*/SKILL.md`も含む**（§3が`AGENTS.md`の二重化回避を観点に
挙げており、`.claude/`配下はレビュー指針そのものなので、漏れると狙った型を拾えない）。コードの変更は[`frontend/`](./frontend/README.md)・[`backend/`](./backend/README.md)の
入口を使う。両方にまたがる変更では、この文書とコード側の入口の両方を使う。

重大度・レビュー出力の形式は[`frontend/README.md`](./frontend/README.md) §2・§4に従い、この文書には
複製しない。

## 1. 運用

- 文書だけの変更でもレビューを省かない。**仕様文書は実装の前提になるので、誤りは実装へそのまま流れる。**
- この入口は、セルフレビュー・`code-reviewer`サブエージェント・Codexの最終チェックが共通で使う。
  入口を増やしたら、[`AGENTS.md`](../../AGENTS.md)の表・`.claude/agents/code-reviewer.md`の手順2・
  [`final-check.md`](./final-check.md)の手順2・[`README.md`](../../README.md)の文書一覧の
  4か所へ接続する。
- 強調記号の崩れは`pnpm lint:markdown`（`scripts/check-markdown.mjs`）が機械的に検出する。対象は
  `docs/`だけでなく、手で書いたすべてのmarkdown（`AGENTS.md`・`contracts/README.md`・`.claude/`等）である。
  **多くは`pnpm lint:markdown --fix`で直せる**（句読点と`**`を入れ替えるだけで、文字そのものは
  変えない）。**句読点は強調の外に出す**（`**強調した**。続き`）。内側に残す形
  （`**強調した。** 続き`）は2026-10-07に採らないと決めた（理由は
  [Plan](../implementation-plans/2026-10-05-markdown-emphasis-lint.md) §5）。
  **ただし`--fix`は強調の範囲を変える**ので、差分では強調の始まりと終わりが対に
  なっているかを見る。対になる括弧・鉤括弧とコードスパンの境界は自動修正の対象外にしてあるが、
  片側だけが範囲の外に出ていないか確認する。レビューでは内容を見る。
- `docs/`だけの変更はCIのweb・apiが走らない（`scripts/ci-changes.mjs`が`docs`へ分類する）。
  そのため**Markdownのジョブだけは変更の種類に関わらず常に走り、CI Gateの必須チェックに入れてある**。
  lefthookのpre-commitでも走るが、そちらは`{staged_files}`ではなく作業ツリー全体を見る。

## 2. 一次資料の扱い

- **検索結果の要約を一次資料として扱わない**。出典URLを取得して本文を読んだものだけを「確認済み」と
  書く。要約から拾った記述は「未確認」として分け、採否の主因に使わない。
- **引用は条件節を落とさない**。条件付きの記述を無条件の約束として引用していないか確認する。
- **出典の版と主張の範囲を一致させる**。APIのv1の資料でv2の挙動を主張していないか、1つのモデルの
  資料でモデル非依存の事実を確定させていないか。
- **出典のページが実際にその主張を裏付けているか**を確認する。並べた出典のうち1つしか裏付けていない、
  という形になっていないか。
- 逆に、**一次資料が示しているのに「未確認」として扱っていないか**も見る。過剰な留保も記録の精度を
  落とす。

## 3. 正本と下流の突き合わせ

- 同じ規則が複数の文書に現れるとき、**条件・範囲・列挙の件数・担当がすべて一致しているか**を
  全出現箇所で確認する。1文書だけを直して他が取り残されていないか。
- **正本より下流のほうが正確なことがある**。その場合は下流へ揃える。どちらが正しいかを根拠で決める。
- **規則の内容を下流へ複製していないか**。下流は「正本が定める」までにし、規則そのものは正本だけに
  置く（`AGENTS.md`の二重化回避）。保持期間と削除の契機は[`privacy.md`](../privacy.md) §5、
  保留事項は[`product.md`](../product.md) §5が正本である。
  **例外**: 方針を1文で言い表した見出し相当の要約は、正本への参照と変更日を添えてあれば複製に
  当たらないものとして扱う（例: 所在地の方針の1文）。**許すのは「方針の1文 ＋ その主語の定義 ＋
  正本へのポインタ」まで**で、**条件・例外・適用範囲を書き写していれば複製**である。その場合は
  正本だけに置き、下流は「射程と例外は正本が定める」までにする（**この一文を書いた直後に例外を
  1つ挙げる、という形になっていないか**を見る）。要約を下流へ置いた場合は、**次にその1文を変えるとき
  全出現箇所を同時に直す**（検索語をPlanへ書き残す）。
  **公開前に終える条件（release gate）は別扱い**で、[`product.md`](../product.md) §5が正本である。
  正本側に同じ条件が書かれていても、役割が違うので二重化ではない。
- **参照先が実在し、指している内容と合っているか**。節番号（`§26`・`項目2・4`）・相対リンク・
  完了条件の番号を、引用元の現在の内容と突き合わせる。**節や項目を増減させた変更では、その節を
  指している全箇所を同時に直す。** 「上記」「下記」の向きも確認する。
  **動くref（`origin/main`等）で計測値を書かない**（コミットのSHAで特定する）。
- **未確定の前提に依存した結論を事実として書いていないか**。前提が未確認なら、結論にもその条件を
  付ける。

## 4. 方針を変える差分

- **変えた方針に依存していた条件・前提・下流タスクが宙に浮いていないか**。方針を緩める変更では、
  その方針を根拠にしていた記述がすべて見直されているかを確認する。
- **複数の条件を同時に満たしながら方針に反する構成が作れないか**を、軸を掛け合わせて具体的に確認する。
- **広い約束に対して条件を軸ごとに列挙していないか**。実物の資料を持たない設計文書の側では網羅
  できないため、単一の要求にして網羅の責任を実装側（またはそれを判断するタスク）へ渡す形が望ましい。
  列挙する場合は「例示であって網羅ではない」と明示されているか。
- **削った内容の行き先があるか**。委ねた先の**確認可能な完了条件**として実際に書かれているかを確認する。
  本文に義務を書いただけで完了条件が無い状態は、渡したことにならない。
- **旧記述が残っていないか**。残っている場合、「変更前はこうだった」と明示された記録なのか直し漏れ
  なのかを区別する。過去のImplementation Planは当時の記録として書き換えない（`AGENTS.md`）が、
  **「現在」を名乗っている箇所は現行方針と食い違う**ので直す対象になる。
- Planの「更新する現行文書」の記録が、**実際の差分と一致しているか。**

## 5. privacy・利用者への約束

- **削除の完了時刻を約束していないか**。約束できるのは「やり直せる期限」と「いつ削除処理を始めるか」
  までである（[`privacy.md`](../privacy.md) §5-2）。
- 外部サービスの自動削除機能の設定値を、消去の期限として扱っていないか。
- **確認済みの範囲と未確認の範囲が区別できているか**。確認していない項目を「問題ない」と扱わない。
- 法令に触れる記述では、**一次資料が示す範囲を超えて断定していないか**。適用の前提（どの場合に
  その義務が生じるか）と、常に重なる義務を区別しているか。

## 6. メンテナンス履歴

- 2026-10-05: 初版作成。PR #52で、**所在地方針の変更に対する**サブエージェントのレビューが10巡しても
  🟠が出続けた。繰り返した型は(1)検索結果の要約を一次資料として扱った、(2)方針を変えたのに依存して
  いた条件を見直さなかった、(3)正本と下流で条件の付き方がずれた、(4)日本語の本文で`**`が強調にならず
  そのまま表示された、の4つ。(4)は`scripts/check-markdown.mjs`で機械的に検出する形にし、
  (1)〜(3)を観点としてここへ残した。
- 2026-10-05: (4)のlintを作り直した。初版は`**`の個数の偶奇で判定していたが、**実際の崩れは個数とは
  無関係**で（`**強調。**続き`は偶数でも壊れる）、CommonMarkのflanking規則で判定する必要があった。
  差し替えたところ**既存の文書に433件の崩れが残っていた**（作り直した後のcheckerを、差し替えた
  時点のコミット`4e937b0`へ当てて計測した。分岐元の`fc8907c`では357件）。**検出方法そのものが
  間違っていると、通っていることが何の保証にもならない**という例として残す。
  経緯と既知の制限は[2026-10-05-markdown-emphasis-lint.md](../implementation-plans/2026-10-05-markdown-emphasis-lint.md)。
- 2026-10-07: この入口とlintを、PR #52から**別のPRへ切り出した**。PR #52のレビュー10巡で出た🟡19件の
  うち、**直近4巡のlint由来はmarkdownのブロック構造の実装精度で、所在地方針の判断とは独立していた**。
  **再発防止の仕組みを本体と同じPRに入れると、仕組み側のレビューで本体が止まる**という記録として残す。
