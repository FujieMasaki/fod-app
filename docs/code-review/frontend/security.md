# 観点: セキュリティ 🔴

Focus on Dot は現時点で Vite によるクライアントSPAである。したがって、クライアントへ
届くコード・値は利用者が取得できる前提で扱う。サーバー、認証、外部APIを追加する変更
では、クライアント側の制御を安全境界とみなさない。個人データの扱いは
[`../../privacy.md`](../../privacy.md)を仕様の正本として確認する。

## 1. 秘密情報と設定 🔴

- [ ] APIキー、アクセストークン、パスワード、秘密鍵、内部専用URLがソースコード・
  テスト・モック・コミット対象ファイルにハードコードされていないか。
- [ ] `VITE_` prefix の環境変数に秘密情報を入れていないか。Vite はこれらをクライアント
  バンドルへ公開する。
- [ ] `.env`、`.env.local`、秘密鍵ファイル、実運用の設定値が差分に含まれていないか。
  必要なら `.env.example` に値を入れないプレースホルダーのみを追加する。
- [ ] 依存追加、CI設定、GitHub Actions の変更で、トークンをログ出力・第三者スクリプト・
  不要な権限へ渡していないか。

## 2. 録音とブラウザ保存 🔴

- [ ] マイク権限を必要なユーザー操作の後にだけ要求し、拒否時の動作を安全に処理しているか。
- [ ] 認証状態の回復、自動の取り直し、ログインの後の戻り先、直接開く・再読み込みで、利用者の操作なしに
  マイクの開始・生成・送信が始まらないか。許可を待っている間に止めた・離れた場合、許可の後に
  streamを止めているか。
- [ ] 録音データ・文字起こし・セッション情報を、要件を超えて `localStorage`、
  `sessionStorage`、IndexedDB、URL、ログへ保存していないか。
- [ ] 保存するデータを最小化し、リセット・削除操作で期待どおりに消去するか。
- [ ] ブラウザ保存データは利用者が改ざんできる。保存値を権限、課金、本人性、または
  サーバーで信頼する値の根拠にしていないか。
- [ ] 保存・送信・削除・匿名化の状態を示す画面文言が、実際の挙動と一致しているか。
  「保存されています」「匿名化済み」のように、実装より強い保持・保護を示していないか。

## 3. API、認証、認可 🔴

- [ ] 新しい API 呼び出しで、ユーザーや録音データを送る先、送る目的、送る項目が最小か。
- [ ] 認証・認可はサーバーまたは信頼できるバックエンドで検証されるか。UI上の非表示、
  ルートガード、`localStorage` のフラグだけに依存していないか。
- [ ] APIレスポンス・エラーをそのまま画面やログへ出さず、内部情報、トークン、他人の
  データを返却していないか。
- [ ] レスポンスはスキーマで検証し、必要なフィールドだけを利用するか。
- [ ] logout・期限切れ・別タブ・利用者の切り替わりの前に始めた処理の結果（Dot生成、保護APIの応答）を、
  後の利用者のstate・画面へ書き戻していないか（始めたときの利用者の世代と照合しているか。現行は
  `useAuth().identityEpoch`）。CSRF tokenの取り直しの後の再送が、別の利用者の認証で
  送られないか。
- [ ] login・logoutの前に送った通信の応答が後から届いて、Cookieを前の状態へ戻さないか（Railsの
  CookieStoreはsessionを読んだ応答でCookieを書き直し、認証・CSRFの確認を通る応答はほぼすべて該当する）。

## 4. 外部入力・表示・遷移 🟠

- [ ] `dangerouslySetInnerHTML` を使う場合、信頼できないHTMLをサニタイズしているか。
- [ ] ユーザー入力、APIレスポンス、`localStorage` 由来の値を HTML として解釈させて
  いないか。
- [ ] 外部URLを `href`、`src`、リダイレクトに使う場合、許可するプロトコル・ホストを
  検証し、`javascript:` などの危険なスキームと open redirect を防いでいるか。
- [ ] 新しい外部リソースを読み込む場合、必要性、信頼性、送信されるデータを確認したか。

## 5. ログとエラー 🟠

- [ ] `console.*`、監視SDK、例外メッセージに録音内容、個人情報、トークン、APIレスポンス
  全文を出力していないか。
- [ ] ユーザー向けエラーは安全で理解可能な文言にし、調査に必要な詳細は機密を除いて
  分離して記録しているか。

## 6. 現在の構成での補足

- `apps/web/src/features/session/session-context.tsx` は、TASK-007で `fod.session.v1` への保存・復元を
  やめ、録音（音声Blob・形式・録音時間）と現在のDotをmemoryにだけ持ち、起動時に `fod.session.v1` を消す。
  録音は、次の録音・整理の成功・利用者の切り替わりで消える。整理のmutationへ渡した分は、整理の画面を離れると
  cacheから消える（`gcTime: 0`。TASK-010）。端末への保存を足すレビューでは、
  個人性・機密性・削除要件と、利用者の切り替わりで消えることを必ず確認する。
- `apps/web/src/components/error-state/error-state.tsx` の既定文言「音声は保存されています」は、
  音声Blobをこのタブのmemoryにだけ持ち、serverへ送らず保存しない現行実装と一致しない。`error-state.test.tsx`もこの文言を検証している。
  [`../../journaling.md`](../../journaling.md)「3. モックと実サービスの区別」が同じ差異を記録しており、
  解消は表示文言と保持・再試行仕様を同時に更新する変更で行う。文言だけを直して
  実際の保持仕様と合わない状態を作らない。
- 認証はRails側をTASK-006で実装した（Webの接続はTASK-007）。Dotなどのプロダクト API と外部AI連携は
  未実装である。backendの
  認証・認可・CSRF・CORS・レート制限は、実装変更時に
  [`../backend/security.md`](../backend/security.md)の観点と実際の認証・配信構成に沿って確認する。
