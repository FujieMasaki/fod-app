## 目的と作業範囲

録音 → 生成 → 保存 → 削除（ゴミ箱・完全削除・退会）の状態遷移は、失敗・中断・再試行・期限での削除が重なり、テストだけでは組み合わせの漏れを見つけにくい。範囲を絞って形式モデルで検証し、開発の流れに取り入れるかを判断する。

アプリ全体には適用しない。候補のツール（Quint / TLA+、XState等の状態機械、Alloy）を比べ、1つの状態遷移で試す。モデル検査で見つかった反例は、実装のtestケースに変換できるかまで確かめる。採用するかどうかと適用範囲は、試行の結果を見て人間が判断する。

## 確認可能な完了条件

- [ ] 試行する状態遷移の範囲と、検証する性質（例: 削除要求の後に音声・Dotが残らない、再試行で二重に保存されない）を決めている。
- [ ] 候補のツールを学習コスト・既存のstackとの相性・反例をtestへ変換できるかで比べ、1つを選んだ理由を記録している。
- [ ] 選んだツールでモデルを書き、検証の結果（反例があればその内容）をPlanに記録している。
- [ ] 反例（なければ境界のケース）を少なくとも1つ、実装のtestへ変換できるか確認している。
- [ ] 開発の流れに取り入れるか、取り入れる場合の範囲と保守の方法を人間が判断し、[architecture.md](../architecture.md)または実装規約へ反映している。
