## 目的と作業範囲

現在のループ（`run-task`・`pr-review-cycle`）は、登録済みのタスクを実装してレビューするためのもので、まだ誰も気づいていない問題を探す段がない。観点を決めた探索的な監査をAIに投げ、見つかった問題を人間が確認してから`docs/tasks`へ起こす流れを作る。

監査の観点は少なくとも次を含める。

- [privacy.md](../privacy.md)と実装の突き合わせ（音声・Dotの保存・送信・削除の漏れ）
- N+1クエリなどの性能
- securityの観点（認証・認可の境界）
- 仕様と実装の不一致

監査の結果は自動でタスク化・PR化せず、人間が採否を判断する。結果の報告に個人データ・秘密情報を含めない。このリポジトリは公開されているため、securityの指摘は修正まで公開の場（`docs/tasks`・PR本文・Issue）に具体的な場所と再現方法を書かない。置き場所と、修正後に記録する手順は着手時に決める。定期実行は既存の`task-scheduler`と衝突しない方法で行うか、手動起動にするかを着手時に決める。ツール・閾値・対象範囲などで複数の有力案がある選択は、AIがPlanで選択肢と推奨を整理したうえで人間の判断に回す（`run-task`の止まる条件「複数の有力案がある」に当たる）。人間のマシンの定期起動（launchd等）を加える場合も、人間の判断とする。

## 確認可能な完了条件

- [ ] 監査の観点・入力・出力の形式を定めたskill（または既存skillの拡張）があり、観点を指定して起動できる。
- [ ] 監査の出力が、根拠（ファイル・行）・重大度・タスク化の候補として人間が採否を判断できる形になっている。
- [ ] securityの指摘を修正まで公開の場に具体的に書かない置き場所と、修正後に記録する手順が決まっている。
- [ ] 採用した候補を[タスクの運用ルール](README.md#運用ルール)どおりに`docs/tasks`へ起こす手順が書かれている。
- [ ] 実行の頻度と起動方法（定期・手動）を決め、`task-scheduler`と同時に動いても作業が衝突しないことを確認している。
- [ ] 少なくとも1つの観点で実際に監査を回し、結果と採否をPlanに記録している。
