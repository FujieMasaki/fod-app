## 目的と作業範囲

設計判断をWeb/APIで共有する正式なrequest / response / error契約と管理・検証方法にする。現在の本文なしPOST /dotを正式契約とみなさない。個別endpointの機能実装はBackendタスク、呼び出し実装はFrontendタスクに分ける。

### TASK-004の履歴決定（契約への入力、2026-09-29）

正本は[dot-history](../dot-history.md) §2「MVPの履歴ルール」、判断の経緯は[TASK-004 Plan §25–§26](../implementation-plans/2026-09-28-task-004-history-design.md)。

- 保存は録音1回=Dot 1件で追記のみ。一覧は日単位に集約した要素を新しい順に返し、集約はserver側で
  完結させる。Web側で日単位の集約を行う契約にしない。
- 続き取得はcursor方式とする。offsetやpage番号は採用しない。parameterとcursorの名称・型・既定値と
  上限（Planの提案値は既定30日分・上限100日分）を本タスクで確定する。
- 日付はAsia/Tokyoの暦日をserverが決め、1日の始まりは0:00 JST。**`date`は`started_at`
  （録音開始操作をserverが受理した時刻・UTC。実際に話し始めた瞬間と完全に一致するとは扱わない。
  定義は[dot-history](../dot-history.md) §2）から算出し、保存時刻からは算出しない**
  （2026-09-29にTASK-004で採用）。
  `started_at`はDotの項目として返し、本人に更新させない。並びと「最新」の判定も`started_at`
  降順・同値ならDotの識別子降順とする。本タスクは`date`と`started_at`の表現形式・項目名・
  schemaを定める。
- **`started_at`は実際の録音開始操作に対応してserverが発行する録音attemptから決める**
  （認証確認の時刻をそのまま使わない）。契約で定めるのは、attemptを発行する操作とresponse、
  送信時の渡し方、**1つのattemptを1件のDot生成にしか使えないこと**、再開始で新しいattemptになる
  こと、別Userのattemptを拒否すること、未送信attemptの期限と期限切れのerror、録音中の失効から
  同一Userで復帰した場合に同じattemptを使えるか、保存方式（serverに保存するか署名済みの値を
  端末のmemoryに置くか）である。serverに保存する方式を採る場合は`privacy.md` §5へ保持・期限・
  削除を追加する。Frontendでの取得・保持・破棄はTASK-010。
- **attemptの一回性は、初回uploadでattemptの識別子を処理の記録へ原子的に関連付けて担保する。**
  署名の検証だけでは同じ値の再送を防げない。同じattemptの再送には、同じ処理を返すか明示的な競合を
  返すかを定める（TASK-003の冪等性の決定と揃える）。**upload受理後の24時間再試行はattemptの再利用
  ではなく処理の記録を使う**契約にし、attemptが使用済みであることを理由に正規の再試行を拒否しない。
  再試行や非同期生成を経ても元のattempt由来の`started_at`を維持する。
- 一覧の要素は、日付・その日のDot件数・最新Dotの識別子のように件数に依存しない固定サイズにする。
  同日の全Dotの識別子を1要素へ並べない（同日の録音件数に上限がないため）。記録のない日は要素を
  返さない。
- **日の詳細は日付をキーに取得する契約にする。**その時点でゴミ箱の外にある同日のDotを返し、
  1日当たりの取得上限・続きの扱い・途中失敗を定める。一覧が返す最新Dotの識別子を、日の詳細へ
  到達する唯一のキーにしない（一覧の取得後にその1件がゴミ箱へ移っても、同日に残るDotへ到達
  できるようにする）。Dot単位の取得も持つ場合は、日付キーの取得との役割を分けて定義する。
- Dayは今日のDotのうち最新1件を表示するため、今日の記録の有無と最新Dotを取得できる契約にする。
  専用endpointにするか一覧の取得で兼ねるかは本タスクで決める。今日の記録がない場合を、
  取得失敗と区別できる応答にする。
- Dot 0件、一覧の読み込み失敗、続きの取得失敗、詳細の取得不可（存在しない・他人・削除済み）を
  区別できるresponseとerrorにする。取得できないDotを別のDotで代替表示させない。
- **日付キーの取得で対象Dotが0件だった場合のresponseを定める。**一覧を取得した後にその日の
  すべてのDotがゴミ箱へ移るか完全削除されると起きる。取得失敗や他人のDotと区別でき、Webが
  「その日に振り返れるDotがない」と示して一覧を取り直せる形にする。
- 任意の月へ直接ジャンプする取得、検索・カテゴリ・期間フィルタ、Week / Monthの集計は契約へ
  追加しない。
- ゴミ箱の中のDotは日単位の一覧に含めず、その日のDot件数にも数えない。同日のすべてのDotが
  ゴミ箱にある日は要素を返さない（下記「2026-09-28のデータ保持・削除の採用」と併せて定義する）。

### 2026-09-28のデータ保持・削除の採用（契約への入力）

[TASK-002 Plan §25](../implementation-plans/2026-09-28-task-002-data-lifecycle.md)で採用した。契約の文面は本タスクで確定する。

- Dotの作成は同一originの`multipart/form-data`で音声を受け取り、Railsが処理の間だけS3東京へ預ける（presigned URLは使わない）。受容するcontent typeを列挙し、最長30分・32MBの上限と超過時のerrorを定義する。音声のbitrateはclientで32kbpsを明示する前提だが、従わないbrowserがあり得るため上限はそれを見込んだ値である。音声のURLは返さない。
- responseはDot（`id` / `date` / `started_at` / `duration` / `sentence` / `summary`）と文字起こし全文。`reflection`と`closing`は契約に含めない（`started_at`は2026-09-29にTASK-004で追加）。
- **更新（編集）のendpointを持つ**（2026-09-29に方針変更）。対象は`sentence`と`summary`だけで、`date`・`started_at`・`duration`は更新させない。編集前の値を返す・戻すためのendpointは作らない（履歴を持たないため）。**空文字は許す（TASK-002で採用済み。必須入力にしない）。**本文の一部を消すための編集という目的を、入力の必須化で損なわない。ここで決めるのは文字数の上限値である。
- **ゴミ箱の契約を持つ**（2026-09-29に追加）。1件ごとの削除は「ゴミ箱へ移す」で、復元と即時の完全削除を別に定義する。ゴミ箱の中のDotは一覧・詳細・Dayのendpointから返さない。ゴミ箱の一覧は別に取得する。ゴミ箱の中のDotは更新させない。受理から7日で削除処理を始めることをresponseで示すかも決める。示す場合、消え終わる時刻として読めない形にする。
- 退会のendpointは本人の再認証を前提にする（上記の再認証要件）。ゴミ箱の中も含めて消す。
- **完全削除と退会**は物理削除で、失敗時に成功と区別できるerrorを返す。完全削除ではそのDotを作った処理の**音声・文字起こし結果・Amazon Transcribeのjob・処理の記録**、退会では本人の全部を消す（2026-09-29にTASK-003で範囲を拡張。契機ごとの削除範囲は[TASK-003 Plan §20](../implementation-plans/2026-09-29-task-003-generation-design.md)の認可表、期間と契機は[privacy.md §5](../privacy.md)が正本）。一部だけ消えた状態を成功として返さない。**ゴミ箱へ移す操作はこれに当たらない**ので、行を消す操作とゴミ箱へ移す操作でresponseとerrorを区別する。S3削除の失敗は完全削除・退会の失敗として返し、ゴミ箱へ移す操作の失敗と混同させない。他人のDotは、ゴミ箱の内外を問わず存在しない扱いにする。
- 再試行・状態取得・削除の認可は、server側が持つ処理の記録で行う。処理IDやkeyの提示だけを権限として扱わない契約にする。記録の項目はTASK-003で確定した（下記）。
- 失敗時の再試行では、音声を預かっている間（期限は[privacy.md §5](../privacy.md)）は録り直さずに同じ音声で再実行できる。再試行の
  期限と、期限切れで録り直しになることをerror契約で区別できるようにする。**期限は相対時間ではなく
  serverが返す日時**とし、clientがそれを表示する。音声が残っていない失敗と区別できるようにする。
- 退会は、受理以降に新しい保存・再試行・結果の確定が起きないことを前提にする。進行中の処理が残った
  まま完了を返さない契約にする。状態遷移と排他の方式はTASK-003と合わせて決める。
- 生成の冪等性と同期/非同期の契約はTASK-003で決まった（下記）。TASK-002は「二重に作られても本人が個別削除できる」ことだけを前提にしている。

### 2026-09-29の生成方式の採用（契約への入力）

[TASK-003 Plan](../implementation-plans/2026-09-29-task-003-generation-design.md)で採用した。契約の文面は本タスクで確定する。

- **非同期で行う。**`POST /api/v1/dots`は処理IDと再試行期限の日時を返して終わり、結果は`GET /api/v1/dots/generations/:処理ID`のpollingで取得する。**pollingの間隔と打ち切りの扱いを契約で決める。**打ち切ってもJobは止まらず、あとから結果を取りに来られる。
- **処理IDと冪等性keyと録音attemptの識別子を同一**とし、**serverが録音開始操作に対して発行する**（2026-09-29にTASK-004の`started_at`採用へ合わせて変更。当初はclient発行のUUIDだった）。`dots`は`(user_id, 処理ID)`のunique制約を持つ。**結果の判定はDotの存在を先に見る**（処理の記録が後片付け待ちで残っていても「処理中」と返さない）。
- 状態の取得では、**処理中・失敗・成功と、再試行できるかどうか、期限の日時**を区別して返す。**次のいずれかに当たると、server側にobjectが残っていても文字起こし全文を返さない: 端末から削除ACKを受け取った、期限を過ぎた、そのDotの完全削除を受理した、退会を受理した**（TASK-003 Plan §27の「返さない条件」）。**いずれもcleanupの完了を待たず、受理した時点から返さない。**理由によってDotが残るかどうかが違うため、errorまたはstatusで区別できる契約にする（**ACK後と保持期間切れはDotが残り、完全削除・退会はDotも残らない**）。
- **処理ID（＝録音attemptの識別子）の形式を契約で定める。**次をすべて満たす必要がある。
  (1) **AWSアカウント内で一意**（S3のkeyとAmazon Transcribeのjob名をここから導くため。利用者単位の一意では足りない）。
  (2) `TranscriptionJobName`の制約を満たす形式（`^[0-9a-zA-Z._-]+`、最大200文字。[StartTranscriptionJob](https://docs.aws.amazon.com/transcribe/latest/APIReference/API_StartTranscriptionJob.html)）。**制約が掛かるのは処理ID単体ではなく、命名規則どおりに組み立てた`<処理ID>-<文字起こし試行番号>`の全体である。**試行番号を付けた後の長さと文字種で判定する。
  (3) `user_id`・email・録音日など、推測できる値や個人情報を含まない。
  **(1)(2)を満たせない形式になる場合は、server発行の別IDを1つ足してAWSの名前をそこから導く**（TASK-003 Plan §20が廃止したprovider IDの層を戻すことに相当する）。
- **文字起こし全文の受領通知（ACK）のendpointを持つ。**clientが全文を`sessionStorage`へ保存し終えたら送り、serverは文字起こし結果とAmazon Transcribeのjobの削除処理を始める（完了時刻は約束しない）。**冪等**とし、対象が既に無くても所有者確認後は成功として扱う。認可は`current_user.dots`と`(user_id, 処理ID)`の両方で行い、処理IDだけで処理の記録を引かない。**IDの一意性にかかわらず、IDを認可情報として扱わず所有者でscopeする**（TASK-003 Plan §27）。通常のCookie認証とCSRFを適用する。
- **完全削除・退会の削除連鎖に、S3の文字起こし結果とTranscribeのjobを加える**（上記「完全削除と退会」の記述を置き換える）。完全削除ではそのDotを作った処理の音声・文字起こし結果・Transcribeのjob・処理の記録、退会では本人の全部を消す。
- **処理の記録の項目を確定する。**処理ID（＝冪等性key＝**録音attemptの識別子**。server発行）・所有者・`started_at`・現在有効な音声と文字起こし結果のobject key・Transcribeのjob名・試行番号・受理時刻・再試行期限・状態・世代番号・最終進捗時刻・失敗の種類。**録音attemptの識別子がAWSアカウント内で一意になる形かを契約で確かめる**（ならない場合はserver発行の別IDを足す）。**記録は後片付けが終わった時点で消える**ので、結果の照会が記録の有無に依存しない契約にする。
- **退会の排他は利用者の行のlockと世代番号で行う**（TASK-003 Plan §20）。契約としては「退会の受理以降は新しい保存・再試行・結果の確定を受け付けない」「進行中の処理が0になるまで完了を返さない」を満たす。
- 失敗時の再試行は、**文字起こし結果が残っていれば生成から、残っていなければ文字起こしからやり直す。**どちらも録り直しにはならない。error契約でこの2つを区別する必要があるかを本タスクで決める。
