# Dot Follow-up Dialogue Specification

この文書は、保存された1件のDotに対して利用者が任意で行う深掘り対話を扱う。録音から最初のDot生成
までの基本flowは[journaling.md](./journaling.md)、複数Dotの履歴体験は[dot-history.md](./dot-history.md)、
個人データの扱いは[privacy.md](./privacy.md)、MVP全体の範囲と位置づけは[product.md](./product.md)を
参照する。

**深掘り対話は現時点で未実装である。** 本文書は体験方針として採用した内容と、実装前に決める設計事項を
区別して記録する。MVP完成条件との関係は[product.md §3](./product.md)を正本とする。

## 1. 採用した体験

基本の利用flowは、まず音声から1件のDotを生成・保存する形を維持する。深掘り対話は、その後に利用者が
任意で追加できる独立した操作であり、毎回のDot生成で対話を必須にしない。

```text
音声を録音
→ 最初のDotを生成・保存
→ 必要な場合だけ「このDotを深掘りする」
→ 音声またはテキストでAIと対話
→ AIがDotへの反映案を提示
→ 利用者が確認
→ 承認した内容だけDotへ反映
```

- 「このDotを深掘りする」操作は、保存済みの特定の1件のDotに紐づく。
- 対話を開始しない利用者にとって、基本flow（journaling.md）の体験・受け入れ条件は変わらない。
- 対話は1件のDotに関連付けられ、複数Dotを横断する対話は今回の対象外とする。

## 2. 対話の位置づけ

対話は、AIに答えや診断を求めるためのものではなく、利用者が自分の考えや感情をもう少し言葉にするための
補助として位置づける。目指すのは問いを与えることではなく、利用者が問いを持てる余白をつくることである。
毎回深く考えることを求めず、「今日はここまで」で終えることも正解として扱う。

- AIは断定的な助言や評価を避け、短い問い返しや発言内容の整理を行う。
- AIは「受け止める → 整理する → 必要なら問いを返す」の順で応答し、最初から答えや助言を出さない。
- 一度に複数の質問を重ねず、問いは原則1つにする。利用者が自分のペースで考えられることを優先する。
- 利用者がAIの問いに答えなくても、体験として問題がないようにする（問いを宿題にしない）。
- 対話は既存のDotに関連付けるが、対話中の発言やAIの回答によってDotを自動更新しない。Dotが変わるのは
  「3. Dotへの反映」で利用者が明示的に承認した場合だけである。

## 3. Dotへの反映

深掘りの結果、AIは次のような変更候補を提示できる。

- タイトルの変更
- 要約の更新
- 新しく言葉になった気づきの追加
- 現在のDotを変更せず、対話だけを終了
- 提案された変更の破棄

Dotへ反映する前に、変更内容を利用者が確認できるようにする。**利用者が明示的に承認した変更だけを保存する。**
AIの提案そのものや対話中の発言だけでDotを書き換えない。

最初に生成された内容を上書きして失わないようにする必要があるため、元のDot、現在のDot、更新履歴を
どのように扱うか（データモデル、版管理、表示方法）は実装前の設計事項として残し、本文書では確定しない。
[TASK-018](./tasks/TASK-018-dot-follow-up-dialogue-design.md)で決める。

## 4. データの区分

深掘り対話を仕様として扱う際、少なくとも次のデータを混同しないように整理する。実装時の保存有無・
保持場所は未決定であり、ここでは区分のみを定義する。

| # | データ | 説明 |
| --- | --- | --- |
| 1 | 最初に生成されたDot | 録音直後にAIが生成した、深掘り対話による変更を経ていない内容。 |
| 2 | Dotに関連付いた深掘り対話 | 対話開始から終了までの、利用者とAIのやり取り。特定の1件のDotに紐づく。 |
| 3 | 現在のDot | 利用者が承認した変更を反映した後の、利用者が実際に見るDotの内容。 |
| 4 | Dotへ反映されなかった発言・提案 | 対話中の発言、およびAIが提示したが利用者が承認しなかった変更案。 |
| 5 | 更新履歴 | 現在のDotへ至るまでの、承認された変更の記録。 |

これら5区分は、対話履歴を保存するかどうかや保持期間が未決定であっても、混同しないための整理である。
「1. 最初に生成されたDot」を上書きせず参照できることと、「3. 現在のDot」が利用者に表示される内容である
ことは、データモデルを設計する際の前提として扱う。

Dotを削除した場合に、関連する対話（#2）・反映されなかった提案（#4）・更新履歴（#5）をどう扱うか
（連鎖削除するか、削除方法・タイミング）は今後の設計対象であり、本文書では確定しない。

TASK-002は、利用者が`sentence`・`summary`を直接編集する場合について「編集前の値を残さない（版も履歴も
持たない）」方針を採用済みである（消したかった実名等が履歴に残るのを避けるため）。深掘り対話による
反映（#5 更新履歴）がこの方針にそのまま従うか、対話由来の変更だけは別の扱いにするかは未確定であり、
本文書では確定しない。[TASK-018](./tasks/TASK-018-dot-follow-up-dialogue-design.md)でTASK-002の方針との
整合を確認する。

## 5. スコープ

最初のDot生成を基本体験とし、深掘り対話はその上に追加する独立した機能として扱う。最初から自由な
無制限チャットを前提にせず、少なくとも次を実装前に決める。

- 1回の深掘り対話で許容する会話回数（上限の要否と具体値）
- 対話の終了方法（利用者が明示的に終了する操作、自動終了の要否）
- 対話の途中離脱時の扱い（未承認の変更案・対話内容が消えるか、残るか）
- 中断した対話の再開可否と方法
- 対話中の送信失敗・AI応答失敗・反映時の保存失敗の扱い

この変更だけでは、AI provider、音声の保存先、文字起こし方式、S3の利用、同期・非同期処理を確定しない。
これらはTASK-002・TASK-003の範囲のまま変更しない。チャット形式のUIと、内部の音声・文字起こし・AI処理の
データフローは、深掘り対話の体験方針とは別の設計事項として整理する。

## 7. 検討中の体験案（未採用）

§1〜2の方針の上で、より具体的な体験として検討している案である。採用は決めておらず、§6の未決定事項と
あわせてTASK-018で判断する。

### 7.1 要約直後に「終える／深掘る」を選べる入口

§1では保存済みのDotから「このDotを深掘りする」を開始する。これに加え、Dotの要約・整理を表示した直後に、
利用者が次の行動を選べる入口を置く案がある。

```text
音声ジャーナリング
→ AIによる要約・整理（Dotとして保存）
→ 利用者が次の行動を選ぶ
   ├─ ここで終える
   └─ もう少し深掘る
        → AIが問いを1つ返す
        → 必要ならAIとの対話を続ける
```

- 「ここで終える」を、深掘りと同等に自然な選択肢として示す。終えることを中断や失敗のように見せない。
- 要約直後の入口を置いても、§1の「保存済みのDotから後で深掘りする」入口を残すかは別途決める。

### 7.2 入口の文言

「深掘りする」はやや硬いため、FoDの世界観に合う柔らかい表現を検討する。候補は次のとおり。

- 終える側: 「ここで終える」
- 深掘る側: 「もう少し見てみる」「この気持ちを探る」「AIと話してみる」

文言は[design-system.md](./design-system.md)の静けさ・可読性の原則に沿って決める。

### 7.3 助言を利用者が求めたときだけ出す

§2のとおり、対話は最初から助言モードにしない。まずは利用者の言葉の反射、感情や葛藤の整理、前提や
思い込みに気づくための問いを中心にする。そのうえで、利用者が必要になった段階で「AIの意見も聞く」の
ような操作によって、明示的に助言を求められるようにする案がある。

- 採用する場合、§2の「AIは断定的な助言や評価を避け」を、利用者が助言を求めた場合の例外として
  どこまで緩めるか（助言の範囲・言い方）を決める必要がある。
