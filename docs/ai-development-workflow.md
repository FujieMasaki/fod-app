# AI を使う開発フロー

AI は実装・調査・レビューを助けるために使う。一方で、要件・設計判断・変更の影響範囲に対する理解と、最終的な判断は人間が持つ。

## 適用する変更

次のいずれかに当てはまる変更では、実装前に機能計画を作る。

- 複数の画面、コンポーネント、または状態にまたがる変更
- 状態遷移、セッション、データ永続化、または API 境界を変更するもの
- 仕様の解釈によって UI や設計が大きく変わり得るもの

文言・スタイルの微調整、明確なバグ修正、既存パターンに沿った小さな変更では計画は不要とする。通常どおり実装、テスト、レビューを行う。

## 実装前

1. 既存のコード、関連ドキュメント、テストを確認する。外部ライブラリの API は一次情報で確認する。
2. AI に、要件の曖昧な点、既存実装との矛盾、設計上の選択肢を一度に解決しようとせず質問させる。仕様を推測で確定しない。
3. [機能計画テンプレート](./feature-plan-template.md) を `docs/plans/` にコピーして、必要な項目を記入する。
4. 人間が、目的、主要な設計判断、変更の影響範囲、受け入れ条件を自分の言葉で説明できることを確認する。不明な点は実装前に解消する。

## 実装とレビュー

1. 計画に沿って実装する。実装中に計画の前提が崩れた場合は、推測で進めず計画を更新して判断する。
2. AI の提案・レビュー指摘は根拠として扱い、機械的に採用しない。仕様、既存設計、実際に起こり得る条件に照らして採用・保留・却下を判断する。
3. 重要な判断は計画の「レビュー判断」に残す。後から「なぜこの実装なのか」を追える状態にする。
4. レビュー時は、次を説明できることを確認する。
   - なぜこの設計・状態管理にしたか
   - 失敗、再試行、境界条件で何が起きるか
   - 変更が UI、状態、API 境界へ与える影響
   - テストが何を保証しているか

## 完了前の確認

変更内容に応じて、次を実行・確認する。

- `pnpm check`
- `pnpm type-check`
- `pnpm test`
- `pnpm build`（リリース相当の変更、または CI 前の最終確認）
- `pnpm ai:review`（レビュー対象の変更。利用できない場合は通常の人間レビューを行う）
- 受け入れ条件に書いたブラウザまたは操作による動作確認

計画の受け入れ条件を満たし、変更内容を人間が説明でき、必要な確認を終えたら完了とする。
