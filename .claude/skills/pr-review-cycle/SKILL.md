# /pr-review-cycle

[AGENTS.md](../../../AGENTS.md)の「Pull Requests」ルール（日本語タイトル/本文、
`pull_request_template.md`準拠、確認なしでpush・PR作成まで進める）を前提に、PR作成後の
レビューループを自動で回す。

## 絶対に守ること

- codexの指摘を握りつぶさない。妥当性を自分で判断し、対応しない場合は理由をPRか会話に明記する。
- `--no-verify`、force push、mainへの直接push、PRのマージをしない。
- 秘密情報（`.env*`、`master.key`等）を読まない・出力しない。
- レビュー→修正ループの反復回数を数え、5回で必ず止まる（無限ループにしない）。

## 手順

### 1. PR作成

1. ベースブランチを決める（通常は`main`。指示があれば従う）。
2. コードの修正を始める前に、必ずベースブランチをリモートの最新に更新する。
   現在ベースブランチにいなければ `git fetch origin <ベースブランチ>:<ベースブランチ>`。
   ベースブランチにいる場合は `git pull --ff-only origin <ベースブランチ>`。これにより、
   後で行う `codex review --base <ベースブランチ>` が古いローカルrefを見て、
   既にマージ済みの変更までレビュー対象に混ぜてしまう事態を防ぐ。
3. `git branch --show-current` で現在のブランチを確認する。ベースブランチと同じなら、
   更新した最新のベースブランチから新しい`<type>/<slug>`ブランチを作って切り替える。
4. 無関係な変更が残っていないか事前に確認する。
   - `git status` で未コミットの変更を確認する。
   - `git log <ベースブランチ>...HEAD --oneline` で、このブランチに今回の依頼と無関係な
     コミットが乗っていないか確認する。
   どちらかで無関係な変更（未コミット・コミット済み問わず）が見つかったら、自動で
   退避・削除・コミットせず、ユーザーに確認する。確認が取れない、または対応方針が
   決まらない場合は、推測で進めず「止まる条件」に従う。
5. 今回の依頼に関係する変更だけをコミットする。`git push -u origin HEAD:<ブランチ名>` で
   送信先を明示してpushし、`gh pr create --base <ベースブランチ>` でPRを作る。以降の手順3で
   使う `codex review --base <ベースブランチ>` と同じベースを指定する。タイトル・本文は
   日本語、`.github/pull_request_template.md` の見出し順（概要 / 取り組んだ理由 /
   （バグ対応なら原因）/ 取り組んだこと / 確認すること）に従う。

### 2. セルフレビュー

`self-review` skillでdiff全体を確認する。該当する [docs/code-review/](../../../docs/code-review/)
のレビュー入口とsecurity観点で見直し、見つかった問題はここで直してコミットし、
`git push origin HEAD:<ブランチ名>` で即座にpushする（後続のcodexレビューが、この時点の
最新コミットを見られるようにする）。

### 3. codexへレビュー依頼

```bash
codex review --base main
```

base branchがmain以外ならそのブランチ名に置き換える。カスタム観点を伝えたい場合も、
`--base <branch>` は落とさずに残す（`codex review --base main "<指示>"`）。省略すると
レビュー対象のdiffが不定になり、途中でコミットを追加した後のレビューが直前の差分だけを
見てしまう。

### 4. 指摘を確認して分類

- 修正が必要な指摘がある → 5へ。
- 指摘なし、または既知の理由で対応不要と判断できる → LGTM扱い。ただしこの時点で7の仕組み化を
  まだ行っていなければ7へ、行っていれば8へ。

### 5. 指摘箇所を修正してコミットし、push する

1コミット = 1関心事を保つ。コミット前に、変更した領域に応じた検証を実行する
（例: frontendは`pnpm --filter @focus-on-dot/web type-check` / `test`、
apps/apiのRailsコードは`cd apps/api && bundle exec rspec` / `bundle exec rubocop`）。
pre-push hookで検証されない領域（Railsのtest/lintなど）は、pushする前に自分で実行して
結果を確認する。検証が通ったらコミットし、送信先を明示して必ずpushする
（`git push origin HEAD:<ブランチ名>`）。pushせずに次に進まない — PRのURLは常に
push済みの最新コミットを指していなければならない。

### 6. 再度セルフレビューしてから3に戻る

手順2と同様にdiffを見直してから、再度codexへレビュー依頼する。3〜6のループの反復回数を数える。
**5回続いても指摘が解消しない場合は、ループを止めて「止まる条件」に従う。**

### 7. 再発防止の仕組み化

同種の指摘を今後受けないよう、次のいずれかに落とし込む。

- `docs/code-review/` の該当レビュー入口へ観点を追記する。
- lintルール・型・testで機械的に検出できるようにする。
- 実装規約（`docs/development/`）や設計文書に判断根拠を残す。

仕組み化するほどではない一過性の指摘なら、その判断をPRか会話に短く記録して8へ進む。
仕組み化する場合は、その変更を別コミットに分けて5・6と同様にコミット・push・
再セルフレビュー・再codexレビューを行う（仕組み化自体の変更もレビューを経ずにPRへ残さない）。
そのレビューで新たな指摘が出れば4に戻って扱う。指摘がなければLGTM確定として8へ進む。

### 8. 完了報告

次の2点を確認してから報告する。

- `git log @{u}..HEAD` が空であること（pushし忘れたコミットがないこと）。
- `git status` がclean であること（コミットし忘れた変更・未追跡ファイルが残っていないこと）。

確認できたら、PRのURL、レビュー→修正の反復回数、仕組み化した内容を短く報告する。

## 止まる条件

- codex review→修正ループが5回続いても収束しない。
- codexの指摘が仕様・設計判断に関わり、人間の判断が必要。
- 秘密情報・外部サービスの設定・課金が必要になった。
- `codex review` 自体が実行できない（未ログイン、認証切れ、ネットワークエラーなど）。原因を
  解消できない場合はリトライを重ねず、その場で止まる。
- 無関係な変更（未コミット・コミット済み問わず）が見つかり、ユーザーに確認できない、
  または対応方針が決まらない。

止まるときは、チャットで反復回数・直近の指摘内容・試したことを示し、判断を仰ぐ。人間が判断したら、
そこから手順を再開する。
