# /human-review-artifact

PRの作成者側が、人間のレビュアー（このプロジェクトでは主にユーザー本人）へ渡すガイドページを作る。
機械が確かめ終えたことと、人間が判断することを切り分け、判断が必要な項目だけを、PRの中の実物を
見ながら確かめられるようにする。あわせて、人間が自分でコードを読んで理解するための地図を載せ、
人間が書いた理解の答え合わせ（手順5）もこの skill で行う。

[PRの分割と人間のレビュー](../../../docs/development/pull-requests.md)に従い、1つのタスク（または
依頼）のPRを複数に分けた場合は、**すべてのPRがLGTMになってから、まとまり全体で1つのページ**を作る。
PRごとには作らない。以下の「PR」は、分けた場合はまとまりの各サブのPRを指す（統合ブランチから`main`への
メインのPRは、行ごとのレビューの対象ではないため、一覧とマージの手順にだけ載せる）。

似た名前の全プロジェクト共通のコマンドとは役割が違う。

| | 誰が使うか | 何をするか |
| --- | --- | --- |
| `/review-guide` | レビュアー | 他人のPRを一問一答でレビューする |
| `/self-review` | PRの作成者 | 変更内容を理解するために解説する |
| この skill | PRの作成者 → レビュアー | レビュアーが判断する項目と、コードを読む地図をページにまとめて渡す。先に解説せず、レビュアーが書いた理解を受けてから答え合わせする |

## 絶対に守ること

- ページの内容は、PR・diff・Plan・CIの実物から書く。実例（コード・JSON・画面の状態）は推測で作らず、
  PRの中から引用する。
- レビュー状態（LGTMのコミット、CIの結果、再確認待ち）は、publishの直前に取り直して正確に書く。
  通っていないものを「通った」と書かない。
- 載せる材料は、PRにある内容（diff・PR本文・Plan・CIの結果）と、レビューの結果を自分の言葉でまとめた
  要約、diffから作ったコードリーディングガイド（ファイルの分類・読む順・問い）に限る。レビュアーの出力やログをそのまま貼らない。
- 秘密情報・個人データをページに載せない。publishの前に引用部分を見直し、秘密情報らしき値があれば
  載せずに止まり、ユーザーに判断を仰ぐ。
- ページは非公開でpublishされる。共有の設定は変えず、ほかの人に見せる方法（ページの共有メニュー）を
  利用者に伝える。publishしてよいのは、ユーザーの依頼（「PR作成して」による`pr-review-cycle`、`docs/tasks/`のタスクIDを
  挙げた依頼による`run-task`（定期実行から起動されたものを含む。定期実行の設定を人間の依頼とみなす）、またはページを作る明示的な依頼）があるときだけ。

## 作るかどうか

**作る**: 機械のレビューでLGTMが出て、人間のレビューへ渡すとき。PRを分けた場合は、すべてのPRが
LGTMになったとき。まだLGTMでないPRが残っていれば作らない。

**作らない**: 軽微な修正（文言・typo、lintの修正、小さなバグ修正、依存の更新など）。目安として、PR本文の
「確認すること」が2項目以下で、仕様や運用の判断を含まない場合は作らない。PRを分けた場合は、まとまり全体の
項目数で判断する。

迷ったら作る。作らなかった場合は、その理由を完了報告に1行で書く。Artifact toolが使えない、または
publishが拒否された場合も、ページを作らずにその旨を完了報告に書く（PRのマージは妨げない）。

## 手順

### 1. 材料を集める

以下はPRごとに集める。先に`git fetch origin <ベースブランチ> <PRのブランチ>`で最新にする。分けた場合のdiffは、各サブのPRのbase（統合ブランチか1つ前のブランチ）との差分にする。
LGTMのコミットは、分けた場合はメインのPRの本文の一覧から、分けていない場合は`pr-review-cycle`でLGTMが確定した
コミットを使う。

- `gh pr view <番号> --json number,title,body,baseRefName,headRefOid,url` と `git diff origin/<ベースブランチ>...origin/<PRのブランチ>`
- `gh pr checks <番号>`（CIの結果）。CIが実行中なら、`gh pr checks <番号> --watch`をBash toolの
  バックグラウンド実行で走らせ、終わるまで待つ。CIが動かないブランチなら、そのことを書く。
  - **CIが失敗していたら、ページを作らない。** `pr-review-cycle`から呼ばれた場合は、同skillの手順6
    （修正）に戻り、手順2・3・4のレビューを経てからこの手順に戻る。単独で頼まれた場合は、失敗を報告して止まる。
- testの件数は、CIのジョブ出力か、このセッションで実行したコマンドの出力から取る。取れない場合や
  testの対象外（Markdownだけの変更など）の場合は、そう書く。
- 関連するImplementation Plan（判断の経緯、人間が判断したQ1〜Qn、実装差異、未対応の指摘）
- レビューの結果（どのコミットでLGTMか、LGTM後に入ったコミットとその内容）

### 2. ページを書く

Artifact toolの規約に従う。最初に`action: "quickstart"`（intentは`other`）を呼び、その結果にある
ページの規約（ライト・ダーク両方のtheme、スマホ幅、CDNの制限、localStorageの扱い）に従ってHTMLを書く。
見た目と動きは参考ページ（PR #45: <https://claude.ai/artifact/KUcAvcCSNudXRp9BBZoo3v>、`action: "read"`で
読める）に合わせる。参考ページを読めない場合は、この手順2に書いた本文の6つの節とArtifactの規約だけに従う。

ページの`<title>`は`PR #<番号> レビューガイド`に固定する（別のセッションから同じページを探す手がかりにする）。
PRを分けた場合は`TASK-XXX レビューガイド`（タスク外なら`PR #<メインのPRの番号> レビューガイド`）にする。
実例として引用するコード・JSON・Mermaidのラベルは、`&`・`<`・`>`をエスケープしてから埋め込む。

ページの上部に、次を出す。

- PR番号・タイトル・コミット、PRへのリンク。分けた場合は、メインのPRへのリンクと、マージの順番に並べたサブのPRの一覧（番号・タイトル・
  base・レビュー対象のファイル数・LGTMのコミット。理由を問わずHEADがLGTMのコミットと違えば、
  HEADと、その間のコミットが何か（前のPRの取り込み、Planの完了の記録など）も並べる）と、[マージの手順](../../../docs/development/pull-requests.md#マージ人間が行う)
  （サブのPRをmerge commitで1番目から順に統合ブランチへマージし、次のPRのbaseを統合ブランチへ付け替える。
  すべて入ったらメインのPRをReady for reviewにし、統合ブランチにレビューを経ていないコミットがないことを
  `git log --first-parent`・サブのPRのmerge commitの第2親・`main`の取り込みの`--remerge-diff`で確かめ、
  CIが通ったら`main`へマージする）
- レビュー状態: どのコミットでLGTMか、CIの結果、testの件数、再確認待ちのもの、人のレビュー待ちであること
- まだ通っていないもの（CI未実行、再確認待ちなど）は、通ったものと見分けられる表示にする
- このページは非公開で、ほかの人に見せるときはページの共有メニューから共有すること

本文は次の6節で構成する。

1. **見るところ・見なくていいところ**
   - 人間が判断すること（仕様・運用・利用者から見た動き）と、機械（lint・型・test・CI・レビュー）が
     確かめ終えたことを切り分ける。
   - 時間の目安を書く。
2. **全体像**
   - Mermaidの図（処理の流れならシーケンス図、手順や分岐ならflowchart）と、変更点・endpointの一覧表。
   - Artifactは`<pre class="mermaid">`をそのまま描画するので、ライブラリは読み込まない。
3. **コードリーディングガイド**
   - 人間がコードを読みながら自分で理解するための「地図」。答えを先に説明せず、コードを読まなくても全部分かる
     解説にしない。書いてよいのは層・ファイルの単位のつながりまでで、関数の中の処理・分岐、関数単位の呼び出し関係、
     設計の理由は書かない（節2「全体像」の図も、関数の単位まで細かくしない）。節の冒頭に「地図を見る → コードを読む →
     自分の理解を書く → チャットで答え合わせを依頼する」の流れを書く。
   - 次の6つの小見出しで構成する。
     1. **変更ファイルの分類**: diffの全ファイルを役割（APIとの通信、データ取得・状態管理、UI、Utility、
        API Schema / 型、Test、Documentationなど、変更に合わせて選ぶ）で分け、各ファイルに役割を1行だけ書く。
        分けた場合は、どのPRで変えたかも書く。lockfile・生成物は1行にまとめる。
     2. **優先して読むファイル**: 3〜5個を読む順に並べ、それぞれ「なぜここから読むと理解しやすいか」と
        「次に進むファイル」を1〜2行で書く。
     3. **大まかなデータフロー**: 主要な流れを、画面・Hook・API関数・Server APIのような層を1行ずつ縦に並べて`↓`で
        つないだASCII図で示す。関数の中の処理と、どこで何を判断しているかは書かない。データフローがない変更では、
        その旨と、代わりに処理の入口から出口までのファイルの並びを書く。
     4. **自分で読むための問い**: 主要なファイルごとに、答えではなく問い（何のために存在する？（関数単位で）どこから
        呼ばれる？何を呼び、何を返す？データはどこから来てどこへ行く？なぜこの責務をここに置く？利用者の
        体験のどこにつながる？）を2〜5個ずつ。紙に答えを書き出せる形にする。節2の図と小見出し3で答えが分かる
        問い（ファイル単位の呼び出し元など）は避け、図だけでは分からないこと（理由・境界・異常系・関数単位の
        つながり）に寄せる。節5「このPRで決めたこと」は人間が自分で判断した内容なので、そこに理由があっても問いから
        外さなくてよい。
     5. **必要なら深掘りするポイント**: pagination・Query Key・cache invalidation・error handling・
        timezone・API schemaなど、変更に関係するものを「ポイント → 見る場所（ファイル・Planの節）」の表にする。
        説明は書かない。
     6. **自分の理解**: 「このPRは何をしている？」「データフロー」「気になった設計」「ユーザー体験とのつながり」
        「分からなかったこと」の5つの入力欄。入力はlocalStorageに保存し（keyはチェック状態のkeyと同じ単位で、
        `-review-`を`-reading-`に替える。例: `pr46-reading-v1`・`task012-reading-v1`）、「答え合わせ用にコピー」
        ボタンで、答え合わせの依頼文と`### 自分の理解`以下のMarkdownをまとめてコピーできるようにする。
        依頼文には、ページの`<title>`と同じ識別子（PR番号またはTASK-XXX）と、PRごとに「PRのURL ＋ ページに書いた
        LGTMのコミット」の組を入れる（分けた場合はサブのPRすべて。別の会話で答え合わせを頼まれても、根拠にするコードを
        特定できるようにする）。入力内容を画面に表示し直すときは`textContent`を使う。
   - 「確認すること」の進み具合のバーには数えない。
   - 見た目は参考ページ（TASK-012: <https://claude.ai/artifact/YHbGyA8hLcWHCZbhXTR4f7>）の「コードリーディングガイド」に合わせる。
     読めない場合は、この節の小見出しとArtifactの規約だけに従う。内容の粒度と依頼文の形は、参考ページよりこのskillの
     記述を優先する。
4. **確認すること**
   - PR本文の「確認すること」を、項目ごとに開閉できるチェックリストにする。分けた場合はPRごとに見出しを
     立て、マージの順番に並べる（人間が1番目のPRから順に見られるようにする）。各項目にPRへのリンクを付ける。
   - 各項目に「説明」「実例（PRの中の実物からの引用）」「OKの基準」を書く。
   - チェック状態はlocalStorageに保存する。読み書きはtry/catchで囲み、保存できなくても表示は崩さない。
     keyはPRごとに分ける（例: `pr46-review-v1`。分けた場合はまとまりで1つ、例: `task008-review-v1`）。
   - チェック状態は項目ごとの識別子（例: `data-key="sandbox"`）に結び付け、識別子に版を含める
     （例: `sandbox@1`）。項目の説明・実例・OKの基準を変えたら版を上げ（`sandbox@2`）、その項目だけ未確認に
     戻す。内容の変わらない項目は版を変えず、チェックを残す。
   - 上部に進み具合のバーを出す。すべてにチェックが付いたら、チャットに貼れる返事をコピーボタン付きで出す。
5. **このPRで決めたこと**: 人間が判断したQ1〜Qnを、理由を1行ずつ添えて並べる。
6. **ファイルの場所**: 見たいもの → pathの表。

### 3. publishする

- このセッションでまだURLを持っていなければ、publishの前にArtifact toolの`action: "list"`で
  手順2で決めたタイトルのページを探す。あれば`action: "read"`で読み、その`url`を指定して更新する
  （同じPRのページを重複させず、閲覧者のチェック状態を引き継ぐため）。
- HTMLはscratchpad（なければOSの一時ディレクトリ。例: `mktemp -d`）に置き、リポジトリには置かない。
- 初回は`icon`と1文の`description`を付けてpublishする。
- 同じPR（分けた場合はまとまりのどれか）に後から修正が入ったら、**同じファイルを編集して再publishする**（URLが変わらず、閲覧者の
  チェック状態も残る）。上部のレビュー状態を更新し、内容が変わった確認項目は版を上げて未確認に戻す。
  CIが後から終わった場合も、結果を反映して再publishする。
- 別の会話から更新する場合は、ArtifactのURLを`url`に渡し、先に`action: "read"`で読んでから更新する。
  URLが手元になければ、Artifact toolの`action: "list"`でタイトルから探す（同じURLを保つため、新しく作らない）。

### 4. 渡す

ページのURLを、何を確かめるページか（項目数と時間の目安）と、非公開であることを添えて渡す。
コードリーディングガイドの「自分の理解」を埋めて貼ってもらえれば答え合わせをすることも、1行で添える。

### 5. 答え合わせ

人間が「自分の理解」を貼って答え合わせを頼んだら、そこで初めて、コードを根拠に次を説明する。根拠にするのは、
依頼文に書かれたLGTMのコミットのコードとし、PRを分けた場合は「PRのURL ＋ LGTMのコミット」の組ごとに次を行う。

1. URLのowner/repoが`gh repo view --json nameWithOwner`と一致することを確かめる。違えば取得せず、人間に確かめる。
2. コミットが手元になければ`git fetch origin <LGTMのコミット>`で取る。取れなければ
   `git fetch origin pull/<番号>/head`で取る（ブランチが消えていても取れる）。それでもLGTMのコミットが手元に
   なければ、その旨を伝えてからPRのHEADを根拠にする（黙ってHEADにすり替えない）。
3. `gh pr view <番号> --json headRefOid`のHEADがLGTMのコミットと違えば、`git diff <LGTMのコミット> <HEAD>`で
   差を確かめ、説明に関わる場合は触れる。

- 間違っている理解（どこが違い、実際はどうなっているか。ファイル・行を示す）
- 抜けている重要ポイント
- 設計上重要な点（なぜこの責務・形にしたか。Planの判断があれば示す）

合っている部分は短く認め、人間の書いた理解を書き直して渡すことはしない。「分からなかったこと」には
個別に答える。

答え合わせの中で、コードの誤りや仕様とのずれが分かった場合（人間の「気になった設計」が実際の問題だった場合を
含む）は、説明で終えない。人間に直すかを確かめ、直すなら人間のレビューの指摘として、[人間がレビューする時機](../../../docs/development/pull-requests.md#人間がレビューする時機)の
流れ（該当するPRで直し、レビューし直す）で扱い、直したらガイドを更新する。`main`へマージ済みなら、新しいPR
（またはタスク）として扱う。
