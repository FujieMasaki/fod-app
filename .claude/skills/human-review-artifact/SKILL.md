# /human-review-artifact

PRの作成者側が、人間のレビュアー（このプロジェクトでは主にユーザー本人）へ渡すガイドページを作る。
機械が確かめ終えたことと、人間が判断することを切り分け、判断が必要な項目だけを、PRの中の実物を
見ながら確かめられるようにする。

似た名前の全プロジェクト共通のコマンドとは役割が違う。

| | 誰が使うか | 何をするか |
| --- | --- | --- |
| `/review-guide` | レビュアー | 他人のPRを一問一答でレビューする |
| `/self-review` | PRの作成者 | 変更内容を理解するために解説する |
| この skill | PRの作成者 → レビュアー | レビュアーが判断する項目をページにまとめて渡す |

## 絶対に守ること

- ページの内容は、PR・diff・Plan・CIの実物から書く。実例（コード・JSON・画面の状態）は推測で作らず、
  PRの中から引用する。
- レビュー状態（LGTMのコミット、CIの結果、再確認待ち）は、publishの直前に取り直して正確に書く。
  通っていないものを「通った」と書かない。
- 載せる材料は、PRにある内容（diff・PR本文・Plan・CIの結果）と、レビューの結果を自分の言葉でまとめた
  要約に限る。レビュアーの出力やログをそのまま貼らない。
- 秘密情報・個人データをページに載せない。publishの前に引用部分を見直し、秘密情報らしき値があれば
  載せずに止まり、ユーザーに判断を仰ぐ。
- ページは非公開でpublishされる。共有の設定は変えず、ほかの人に見せる方法（ページの共有メニュー）を
  利用者に伝える。publishしてよいのは、ユーザーの依頼（「PR作成して」による`pr-review-cycle`、または
  ページを作る明示的な依頼）があるときだけ。

## 作るかどうか

**作る**: 機械のレビューでLGTMが出て、人間のレビューへ渡すとき。

**作らない**: 軽微な修正（文言・typo、lintの修正、小さなバグ修正、依存の更新など）。目安として、PR本文の
「確認すること」が2項目以下で、仕様や運用の判断を含まない場合は作らない。

迷ったら作る。作らなかった場合は、その理由を完了報告に1行で書く。Artifact toolが使えない、または
publishが拒否された場合も、ページを作らずにその旨を完了報告に書く（PRのマージは妨げない）。

## 手順

### 1. 材料を集める

- `gh pr view <番号> --json number,title,body,headRefOid,url` と `gh pr diff <番号>`
- `gh pr checks <番号>`（CIの結果）と、実行したtestの件数。CIが実行中なら終わるまで待つ
  （`gh pr checks <番号> --watch`）。CIが動かないブランチなら、そのことを書く。
- 関連するImplementation Plan（判断の経緯、人間が判断したQ1〜Qn、実装差異、未対応の指摘）
- レビューの結果（どのコミットでLGTMか、LGTM後に入ったコミットとその内容）

### 2. ページを書く

Artifact toolの規約に従う。最初に`action: "quickstart"`（intentは`other`）を呼び、その結果にある
ページの規約（ライト・ダーク両方のtheme、スマホ幅、CDNの制限、localStorageの扱い）に従ってHTMLを書く。
見た目と動きは参考ページ（PR #45: <https://claude.ai/artifact/KUcAvcCSNudXRp9BBZoo3v>、`action: "read"`で
読める）に合わせる。参考ページを読めない場合は、この skill の5節の構成とArtifactの規約だけに従う。

ページの上部に、次を出す。

- PR番号・タイトル・コミット、PRへのリンク
- レビュー状態: どのコミットでLGTMか、CIの結果、testの件数、再確認待ちのもの、人のレビュー待ちであること
- まだ通っていないもの（CI未実行、再確認待ちなど）は、通ったものと見分けられる表示にする
- このページは非公開で、ほかの人に見せるときはページの共有メニューから共有すること

本文は次の5節で構成する。

1. **見るところ・見なくていいところ**
   - 人間が判断すること（仕様・運用・利用者から見た動き）と、機械（lint・型・test・CI・レビュー）が
     確かめ終えたことを切り分ける。
   - 時間の目安を書く。
2. **全体像**
   - Mermaidの図（処理の流れならシーケンス図、手順や分岐ならflowchart）と、変更点・endpointの一覧表。
   - Artifactは`<pre class="mermaid">`をそのまま描画するので、ライブラリは読み込まない。
3. **確認すること**
   - PR本文の「確認すること」を、項目ごとに開閉できるチェックリストにする。
   - 各項目に「説明」「実例（PRの中の実物からの引用）」「OKの基準」を書く。
   - チェック状態はlocalStorageに保存する。読み書きはtry/catchで囲み、保存できなくても表示は崩さない。
     keyはPRごとに分ける（例: `pr46-review-v1`）。
   - チェック状態は項目ごとの識別子（例: `data-key="sandbox"`）に結び付け、識別子に版を含める
     （例: `sandbox@1`）。項目の説明・実例・OKの基準を変えたら版を上げ（`sandbox@2`）、その項目だけ未確認に
     戻す。内容の変わらない項目は版を変えず、チェックを残す。
   - 上部に進み具合のバーを出す。すべてにチェックが付いたら、チャットに貼れる返事をコピーボタン付きで出す。
4. **このPRで決めたこと**: 人間が判断したQ1〜Qnを、理由を1行ずつ添えて並べる。
5. **ファイルの場所**: 見たいもの → pathの表。

### 3. publishする

- HTMLはscratchpad（なければOSの一時ディレクトリ。例: `mktemp -d`）に置き、リポジトリには置かない。
- 初回は`icon`と1文の`description`を付けてpublishする。
- 同じPRに後から修正が入ったら、**同じファイルを編集して再publishする**（URLが変わらず、閲覧者の
  チェック状態も残る）。上部のレビュー状態を更新し、内容が変わった確認項目は版を上げて未確認に戻す。
  CIが後から終わった場合も、結果を反映して再publishする。
- 別の会話から更新する場合は、ArtifactのURLを`url`に渡し、先に`action: "read"`で読んでから更新する。

### 4. 渡す

ページのURLを、何を確かめるページか（項目数と時間の目安）と、非公開であることを添えて渡す。
