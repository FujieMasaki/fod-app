# /human-review-artifact

PRの作成者側が、人間のレビュアー（このプロジェクトでは主にユーザー本人）へ渡すガイドページを作る。
機械が確かめ終えたことと、人間が判断することを切り分け、判断が必要な項目だけを、PRの中の実物を
見ながら確かめられるようにする。

[PRの分割と人間のレビュー](../../../docs/development/pull-requests.md)に従い、1つのタスク（または
依頼）のPRを複数に分けた場合は、**すべてのPRがLGTMになってから、まとまり全体で1つのページ**を作る。
PRごとには作らない。以下の「PR」は、分けた場合はまとまりの各PRを指す。

似た名前の全プロジェクト共通のコマンドとは役割が違う。

| | 誰が使うか | 何をするか |
| --- | --- | --- |
| `/review-guide` | レビュアー | 他人のPRを一問一答でレビューする |
| `/self-review` | PRの作成者 | 変更内容を理解するために解説する |
| この skill | PRの作成者 → レビュアー | レビュアーが判断する項目をページにまとめて渡す |

## 絶対に守ること

- ページの内容は、PR・diff・Plan・CIの実物から書く。実例（コード・JSON・画面の状態）は推測で作らず、
  PRの中から引用する。
- レビュー状態（LGTMのコミット、CIの結果、再確認待ち）は、publishの直前に取り直して正確に書く。
  通っていないものを「通った」と書かない。
- 載せる材料は、PRにある内容（diff・PR本文・Plan・CIの結果）と、レビューの結果を自分の言葉でまとめた
  要約に限る。レビュアーの出力やログをそのまま貼らない。
- 秘密情報・個人データをページに載せない。publishの前に引用部分を見直し、秘密情報らしき値があれば
  載せずに止まり、ユーザーに判断を仰ぐ。
- ページは非公開でpublishされる。共有の設定は変えず、ほかの人に見せる方法（ページの共有メニュー）を
  利用者に伝える。publishしてよいのは、ユーザーの依頼（「PR作成して」による`pr-review-cycle`、`docs/tasks/`のタスクIDを
  挙げた依頼による`run-task`（定期実行から起動されたものを含む。定期実行の設定を人間の依頼とみなす）、またはページを作る明示的な依頼）があるときだけ。

## 作るかどうか

**作る**: 機械のレビューでLGTMが出て、人間のレビューへ渡すとき。PRを分けた場合は、すべてのPRが
LGTMになったとき。まだLGTMでないPRが残っていれば作らない。

**作らない**: 軽微な修正（文言・typo、lintの修正、小さなバグ修正、依存の更新など）。目安として、PR本文の
「確認すること」が2項目以下で、仕様や運用の判断を含まない場合は作らない。PRを分けた場合は、まとまり全体の
項目数で判断する。

迷ったら作る。作らなかった場合は、その理由を完了報告に1行で書く。Artifact toolが使えない、または
publishが拒否された場合も、ページを作らずにその旨を完了報告に書く（PRのマージは妨げない）。

## 手順

### 1. 材料を集める

以下はPRごとに集める。分けた場合のdiffは、各PRのbase（1つ前のブランチ）との差分にする。

- `gh pr view <番号> --json number,title,body,baseRefName,headRefOid,url` と `git diff origin/<ベースブランチ>...origin/<PRのブランチ>`
- `gh pr checks <番号>`（CIの結果）。CIが実行中なら、`gh pr checks <番号> --watch`をBash toolの
  バックグラウンド実行で走らせ、終わるまで待つ。CIが動かないブランチなら、そのことを書く。
  - **CIが失敗していたら、ページを作らない。** `pr-review-cycle`から呼ばれた場合は、同skillの手順6
    （修正）に戻り、手順2・3・4のレビューを経てからこの手順に戻る。単独で頼まれた場合は、失敗を報告して止まる。
- testの件数は、CIのジョブ出力か、このセッションで実行したコマンドの出力から取る。取れない場合や
  testの対象外（Markdownだけの変更など）の場合は、そう書く。
- 関連するImplementation Plan（判断の経緯、人間が判断したQ1〜Qn、実装差異、未対応の指摘）
- レビューの結果（どのコミットでLGTMか、LGTM後に入ったコミットとその内容）

### 2. ページを書く

Artifact toolの規約に従う。最初に`action: "quickstart"`（intentは`other`）を呼び、その結果にある
ページの規約（ライト・ダーク両方のtheme、スマホ幅、CDNの制限、localStorageの扱い）に従ってHTMLを書く。
見た目と動きは参考ページ（PR #45: <https://claude.ai/artifact/KUcAvcCSNudXRp9BBZoo3v>、`action: "read"`で
読める）に合わせる。参考ページを読めない場合は、この手順2に書いた本文の5つの節とArtifactの規約だけに従う。

ページの`<title>`は`PR #<番号> レビューガイド`に固定する（別のセッションから同じページを探す手がかりにする）。
PRを分けた場合は`TASK-XXX レビューガイド`（タスク外なら`PR #<1番目の番号>〜#<最後の番号> レビューガイド`）にする。
実例として引用するコード・JSON・Mermaidのラベルは、`&`・`<`・`>`をエスケープしてから埋め込む。

ページの上部に、次を出す。

- PR番号・タイトル・コミット、PRへのリンク。分けた場合は、マージの順番に並べたPRの一覧（番号・タイトル・
  base・レビュー対象のファイル数・LGTMのコミット。前のPRを取り込んだ後のHEADがLGTMのコミットと違えば、
  それも並べる）と、[マージの手順](../../../docs/development/pull-requests.md#マージ人間が行う)
  （merge commitで、1番目から順に、次のPRのbaseを`main`へ付け替えてからマージする）
- レビュー状態: どのコミットでLGTMか、CIの結果、testの件数、再確認待ちのもの、人のレビュー待ちであること
- まだ通っていないもの（CI未実行、再確認待ちなど）は、通ったものと見分けられる表示にする
- このページは非公開で、ほかの人に見せるときはページの共有メニューから共有すること

本文は次の5節で構成する。

1. **見るところ・見なくていいところ**
   - 人間が判断すること（仕様・運用・利用者から見た動き）と、機械（lint・型・test・CI・レビュー）が
     確かめ終えたことを切り分ける。
   - 時間の目安を書く。
2. **全体像**
   - Mermaidの図（処理の流れならシーケンス図、手順や分岐ならflowchart）と、変更点・endpointの一覧表。
   - Artifactは`<pre class="mermaid">`をそのまま描画するので、ライブラリは読み込まない。
3. **確認すること**
   - PR本文の「確認すること」を、項目ごとに開閉できるチェックリストにする。分けた場合はPRごとに見出しを
     立て、マージの順番に並べる（人間が1番目のPRから順に見られるようにする）。各項目にPRへのリンクを付ける。
   - 各項目に「説明」「実例（PRの中の実物からの引用）」「OKの基準」を書く。
   - チェック状態はlocalStorageに保存する。読み書きはtry/catchで囲み、保存できなくても表示は崩さない。
     keyはPRごとに分ける（例: `pr46-review-v1`。分けた場合はまとまりで1つ、例: `task008-review-v1`）。
   - チェック状態は項目ごとの識別子（例: `data-key="sandbox"`）に結び付け、識別子に版を含める
     （例: `sandbox@1`）。項目の説明・実例・OKの基準を変えたら版を上げ（`sandbox@2`）、その項目だけ未確認に
     戻す。内容の変わらない項目は版を変えず、チェックを残す。
   - 上部に進み具合のバーを出す。すべてにチェックが付いたら、チャットに貼れる返事をコピーボタン付きで出す。
4. **このPRで決めたこと**: 人間が判断したQ1〜Qnを、理由を1行ずつ添えて並べる。
5. **ファイルの場所**: 見たいもの → pathの表。

### 3. publishする

- このセッションでまだURLを持っていなければ、publishの前にArtifact toolの`action: "list"`で
  手順2で決めたタイトルのページを探す。あれば`action: "read"`で読み、その`url`を指定して更新する
  （同じPRのページを重複させず、閲覧者のチェック状態を引き継ぐため）。
- HTMLはscratchpad（なければOSの一時ディレクトリ。例: `mktemp -d`）に置き、リポジトリには置かない。
- 初回は`icon`と1文の`description`を付けてpublishする。
- 同じPR（分けた場合はまとまりのどれか）に後から修正が入ったら、**同じファイルを編集して再publishする**（URLが変わらず、閲覧者の
  チェック状態も残る）。上部のレビュー状態を更新し、内容が変わった確認項目は版を上げて未確認に戻す。
  CIが後から終わった場合も、結果を反映して再publishする。
- 別の会話から更新する場合は、ArtifactのURLを`url`に渡し、先に`action: "read"`で読んでから更新する。
  URLが手元になければ、Artifact toolの`action: "list"`でタイトルから探す（同じURLを保つため、新しく作らない）。

### 4. 渡す

ページのURLを、何を確かめるページか（項目数と時間の目安）と、非公開であることを添えて渡す。
